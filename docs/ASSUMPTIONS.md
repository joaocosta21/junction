# Assumptions and next steps

This page lists what we assumed to build the gateway: where Valio Aimo's mock is silent, where we chose a value, and where we chose one reading of the data over another. Each row says why, what would change it, and where it lives in the code.

- **Numbers** say where they come from. "Catalog" means counted over all 17,546 products of the product file. "Sample" means a sample of live calls, which moves with the clock.
- **Q1 to Q13** are the questions for Valio's mentors in `AIMO/BOOTH-QUESTIONS.md`. Ids such as **T03-1** are questions raised during the overnight build, in the same file.
- **Illustrative** marks a value we chose ourselves. The mock has no customers, limits or approvers, so every such value is ours and is labelled as ours on the pages too.
- The technical choices, what is out of scope, and the next steps follow the table.

## What the mock does not tell us

Each of these is a row above.
- Whether an order can be placed at all: there is no order endpoint.
- What a customer may spend or who approves: the customer string changes nothing.
- The stock of Terminal products and of Stock products with a very large value.
- When the rest of a partly available line could arrive: one schedule line per product.
- Whether deposits are in the price, and whether a variable-weight invoice uses the ordered weight.
- What the category digits mean, and their names.
- Allergen data for 46.2% of products (catalog), and whether missing data means "declared nothing".

## Technical choices, each with its reason

| Choice | Reason |
|---|---|
| Python 3.13, FastAPI, Pydantic v2 | The team knows Python. FastAPI generates OpenAPI 3.1 from the typed models, so the published interface cannot drift from the code. |
| **The model never decides a price, a quantity, an allergen status or a verdict** | Those come from deterministic code that can be tested and audited. |
| Policy as YAML: fixed rules plus one profile per buyer | The guardrails can be read and changed without touching code; the policy hash in each event shows which version applied. |
| REST and MCP over one service object | Any agent can use the gateway, by OpenAPI or by MCP, and the rules live in one place. |
| Bearer tokens; the profile comes from the token | An agent cannot choose its own authority. |
| Audit events in CloudEvents 1.0, hash-chained | A documented open envelope, and a log that shows tampering. |
| Errors as RFC 9457 problem details; `Idempotency-Key` on orders | Agents branch on a stable error type, and a retry never places a second order. |
| SQLite behind a repository interface | No service to provision; PostgreSQL can be added behind the same interface. |
| Replay mode with a pinned clock | The demo survives the mock being down or every cut-off having passed. |
| Server-rendered pages, no external asset, a strict Content-Security-Policy | One process, no build step, nothing loaded from elsewhere. |
| Gemini through the official SDK | Structured output turns pasted text into the typed request; function calling drives the buyer agent. |
| Synchronous ports | One style everywhere; SQLite, `httpx` and the Gemini SDK all have synchronous clients. |

## Out of scope

- Recipe to order, proactive selling, and standing-order drift: every input would be invented.
- Delivery split across dates: the mock cannot show it.
- Ranking by delivery reliability or carbon: the values are loaded but not used. All 91 products of the milk category carry the same carbon value, 1.1 (catalog).
- Payment, and agentic payment standards: the brief names them as context, not as required.
- Sending an order to Valio: there is nowhere to send it.
- Two stretch tasks were not built: orders and audit trail in Aiven PostgreSQL, and web evidence for missing allergen data through Context.dev.

## Next steps toward production

The full list, with the standards each step would use, is in `docs/STANDARDS.md`.
1. An order message Valio's systems can take, in an open e-procurement format such as Peppol BIS Ordering; and Valio's answer on what an accepted order commits to.
2. Real customer limits and approvers in place of the illustrative profiles.
3. Origin and Host checks on the MCP endpoint, then OAuth-issued tokens and a login for the pages.
4. An audit trail the other party can check: canonical JSON hashes, the chain's head handed over with each order, PostgreSQL with a trigger that refuses changes.
5. More than one process: a unit of work in the store and a shared rate limiter.
6. The buyer's needed-by date passed to Valio's `requestedDate`.
7. Signed supplier statements for price, stock and origin.
8. Real addresses for the problem types and an owned prefix for the event types.
9. Delivery reliability and sustainability in the comparison.
10. A deadline for a whole agent run and a cap on the model's output length.
