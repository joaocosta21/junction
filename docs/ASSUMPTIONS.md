# Assumptions and next steps

This page lists what we assumed to build the gateway: where Valio Aimo's mock is silent, where we chose a value, and where we chose one reading of the data over another. Each row says why, what would change it, and where it lives in the code.

- **Ours** marks a value, a word list or a rule we chose ourselves. The mock has no customers, limits, approvers or order history, so every such value is ours, and the pages label it as ours too.
- **Numbers** say where they come from. "Catalog" means counted over all 17,546 products of the product file. "Recording" means the recorded copies of Valio's answers used in replay: 1,163 products in two recordings of the same Saturday, read as one. 769 are in `fixtures/valio/2026-11-14-demo` (recorded Sat 14 Nov 2026 at 02:52 Helsinki time, which gives the clock) and 394 baking products in `fixtures/valio/2026-11-14-baking` (21:12). "Sample" means a sample of live calls made on 13 and 14 Nov, written down in `AIMO/FINDINGS.md` and not measured again since.
- **A model may read a sentence; fixed rules check it, stand in for it, and decide.** A request in free text is read by a model when one is configured, by a labelled recording of that sentence, or by fixed rules (`src/tta/agent/rules_reader.py`), in that order, and every answer says who read it. Whoever reads, every price, quantity, allergen status and verdict is deterministic code. The rows "Reader" say exactly how; `GET /healthz` → `agent_reader` says what reads sentences on a given gateway.
- **Nothing here is signed by Valio Aimo**, no payment is taken, and no order reaches Valio: the rows "Order step", "Signatures" and "Payment" say what exists instead.
- First checked against the code at commit `c2106fe` (Sat 14 Nov 2026, evening); brought to the code at commit `94b21a5` on Sun 15 Nov 2026, about 03:00, against a local gateway in replay. What is ours in the demonstration is summed up under "Assumptions of the demonstration, in short", and what a pilot would add under "Next steps toward production". The questions Q1 to Q16 are in `AIMO/BOOTH-QUESTIONS.md` and `AIMO/BOOTH-NOW.md`.

## What the mock does not tell us

Each of these is a row above.

## Technical choices, each with its reason

| Choice | Reason |
|---|---|
| Python 3.13, FastAPI, Pydantic v2 | The team knows Python. FastAPI generates OpenAPI 3.1 from the typed models, so the published interface cannot drift from the code. |
| A model may read free text, with fixed rules as its check and its fallback; code decides every price, quantity, allergen status and verdict | A reading is checked against the text before anything is built on it, the rules and the decisions can be tested and audited, and a text the rules cannot read becomes a question instead of a guess. |
| Policy as YAML: fixed rules plus one profile per buyer | The guardrails can be read and changed without touching code; the policy hash in each event shows which version applied. |
| REST and MCP over one service object | Any agent can use the gateway, by OpenAPI or by MCP, and the rules live in one place. |
| Bearer tokens; the profile comes from the token | An agent cannot choose its own authority. |
| Audit events stored in a CloudEvents 1.0 envelope, hash-chained | A documented open envelope, and a log that shows tampering. `GET /v1/audit` answers a reader's view of each event (`id`, `type`, `time`, `actor`, `sentence`, `rule_ids`, `facts`, `hash`), not the stored envelope: the trail cannot be loaded as it is answered into a tool that reads CloudEvents. |
| Errors as RFC 9457 problem details; `Idempotency-Key` on orders | Agents branch on a stable error type, and a retry never places a second order. |
| Offers and orders signed by the gateway, key published as a JWK set | A buyer can check a record was not changed after it was issued. The key is a demo key unless the operator sets one. |
| SQLite behind a repository interface; PostgreSQL behind the same interface when `DATABASE_URL` is set | SQLite needs no service. In PostgreSQL the database itself refuses changes to audit events, and the supplier's view is defined in SQL. What of it ran against a database and what did not is in `docs/AIVEN.md`. |
| Replay with a pinned clock | The demo gives the same answer at any hour and survives the mock being down. |
| Server-rendered pages and a static shop page, no external asset | One process, no build step, nothing loaded from elsewhere. |

## Assumptions of the demonstration, in short

What in the demonstration is ours and stated as such. Each is a row above.
- **The order step is ours, by design.** Valio Aimo's test API gives price and availability; "ordered" is a signed record in the gateway's order book and commits nobody. No payment is taken.
- **The data is a recording at a clock we chose.** 1,163 products recorded on Sat 14 Nov 2026, judged at Thu 12 Nov 2026 14:15 in the demo. Live mode asks Valio Aimo's API for each request and is not what the demo shows.
- **The customers are synthetic** and every limit value is illustrative: names, people, past orders, standing orders, spend limits.
- **The signature is the gateway's, with a demo key** that is new at every start. Nothing is signed by Valio Aimo.
- **The demo pages have no login.** A page acts as the customer's person it shows, so on a page anyone can confirm as any of the customer's people. That an agent cannot approve is enforced over REST and MCP, where a token says who calls.
- **One person confirms.** At the hotel and the bakery that person holds every role; the ward and the school have a dietitian as the second person.
- **Ordering alone is off for the four customers**, because Valio Aimo asked for a person on every order. It is shown on `/shop` → Settings, in a browser's own order book.
- **Who reads a sentence depends on the gateway's settings.** A model is asked first when one is configured; otherwise, or when it does not answer, a recording or the fixed rules read it (the rules read English and ask when they cannot read). `GET /healthz` → `agent_reader` says which. The figures of the demo script were measured with no key. A model never decides what may be ordered.
- **Valio Aimo's own suggestion is a related product**, because the product data carries no "new" or "seasonal" mark.
- **Delivery in one piece.** The test API gives one schedule line per product, so a delivery split across dates is not shown.
- **The shop page was walked by a script** in headless Chrome at 1440 × 900 on 15 Nov, with one phone-width pass of the first load and scenario 1 (`AIMO/build/replan/REVIEW.md`, section BW), before the last changes to the page; no person on the team has signed off its layout at phone width.

## Next steps toward production

What a pilot would add. None of these exists today; each says what it starts from. The standards each step would use are in `docs/STANDARDS.md`.
1. **An order message Valio Aimo's systems can take**, in an open e-procurement format such as Peppol BIS Ordering, and Valio's answer on what an accepted order commits to. Starts from: the order record already keeps the lines, the prices with their validity and the stock and delivery statements it relied on.
2. **Valio Aimo signing its own statements** of price, stock and origin (a Verifiable Credential is one form), so the trust protocol rests on the supplier's signature and not on this gateway's. Starts from: every line already carries a status per statement, and every record a signature a buyer can check.
3. **Real customers**, limits, approvers and order history in place of the four synthetic files; the suggestion thresholds set on real orders.
4. **People signing in with their own accounts**: OAuth-issued tokens, a login for the pages, a Host check on the MCP endpoint, and a second signer above an amount at customers where one person now holds every role. Starts from: over REST the roles, the refusals and the log of who decided already work per token; outside `dev` and `demo` no page is mounted.
5. **Stored orders and offers tied to their audit entries**, so a record changed in the database no longer gets a valid signature. Today a database writer can change a stored order and the gateway signs what it reads. Starts from: the hash chain and the pinned hashes; it needs one field on a hashed model.
6. **The audit head held by another party**: run the scheduled witness, and hand the head to buyer and Valio with each order; one canonical JSON form (RFC 8785) for the chain as for the signatures; the trail answered as CloudEvents at the interface (today `GET /v1/audit` answers a reader's view, and the envelope is how events are stored).
7. **A nutrition standard for schools and hospitals.** Today a substitute whose formula or nutrients differ goes to the dietitian at the ward and the school. Next: the standard as rules, with a dietitian or a biomedical reviewer signing the formula tolerances, the fat-source word list, the dietary-claim list and the flavour and use word lists.
8. **The buyer's own share for a dearer substitute**: rule P-05 already sends a substitute that costs more than 25% above the product asked for to a person; the 25% is ours where a profile sets none (row "Substitutes"). Next: a setting of its own on the Settings page.
9. **New and seasonal products marked in the data**, with a flavour and a use, so none of them is read from names; Valio Aimo's own suggestion can then be what the brief calls "a new or seasonal product".
10. **Recipes around a seasonal ingredient.** Today the buyer names the dish, or an ingredient and gets the dishes that use it; nothing knows a season. It needs the season mark of step 9.
11. **A scheduler for standing orders**, and a stock watch that warns a kitchen before it asks. Today each renewal is asked for by a person or an agent, and suggestions, the regular-order alert and a stock-out's substitute all answer a request or a page being opened. Starts from: the renewal, the drift rule and the suggestions are functions a timer can call.
12. **An origin and a price per unit read from the sentence** ("Finnish milk", "under €2 a litre") as typed fields of the request, and **sentences in Finnish and Swedish**. A spend limit named for the whole request is already read (row "The reader"). Today each is asked about or refused with a sentence, never guessed (row "Reader"). Starts from: the product names exist in Finnish and the origin is a field of every line.
13. **A demo agent that orders alone over REST and MCP**: a demo customer with the setting on, named in `/llms.txt`. Today it is shown on `/shop` only (row "Person on every order").
14. **The model's readings measured on the same reading table as the fixed rules** (today the table measures the rules alone), for the sentences the rules ask about and for a photo of an order list.
15. **A fresh offer when the re-check at approval time fails** (today the order keeps waiting and the approver picks another option or rejects); a delete route for standing orders.
16. Run the PostgreSQL proof and the live tests of the supplier view against a database, then a runtime login that does not own the tables.
17. More than one process: a rate limiter and a call budget shared between them.
18. The buyer's needed-by date passed to Valio's `requestedDate`, once the API honours it; a delivery split across dates once the API can state one.
