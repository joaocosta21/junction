# Assumptions and next steps

This page lists what we assumed to build the gateway: where Valio Aimo's mock is silent, where we chose a value, and where we chose one reading of the data over another. Each row says why, what would change it, and where it lives in the code.

- **Ours** marks a value, a word list or a rule we chose ourselves. The mock has no customers, limits, approvers or order history, so every such value is ours, and the pages label it as ours too.
- **Numbers** say where they come from. "Catalog" means counted over all 17,546 products of the product file. "Recording" means the 769 products of the recorded copy of Valio's answers used in replay (`fixtures/valio/2026-11-14-demo`, recorded Sat 14 Nov 2026 at 02:52 Helsinki time). "Sample" means a sample of live calls made on 13 and 14 Nov, written down in `AIMO/FINDINGS.md` and not measured again since.
- **No model was called for this build.** Requests in free text are read by fixed rules (`src/tta/agent/rules_reader.py`). The code for a language model is still in the repository as an option for whoever deploys the gateway; the row "Reader" says exactly what it does.
- **Nothing here is signed by Valio Aimo**, no payment is taken, and no order reaches Valio: the rows "Order step", "Signatures" and "Payment" say what exists instead.
- Checked against the code at commit `c2106fe` (Sat 14 Nov 2026, evening). The questions Q1 to Q16 are in `AIMO/BOOTH-QUESTIONS.md` and `AIMO/BOOTH-NOW.md`.

## What the mock does not tell us

Each of these is a row above.
- Whether an order can be placed at all: there is no order endpoint.
- Who the customers are, what they may spend, who approves and what they ordered before: all of it is synthetic here.
- The stock of Terminal products and of Stock products with a very large value.
- When the rest of a partly available line could arrive: one schedule line per product.
- Whether deposits are in the price.
- What the category digits mean, and their names.
- Which products are new or seasonal.
- Allergen data for 8,110 of 17,546 products (catalog), and whether missing data means "declared nothing".

## Technical choices, each with its reason

| Choice | Reason |
|---|---|
| Python 3.13, FastAPI, Pydantic v2 | The team knows Python. FastAPI generates OpenAPI 3.1 from the typed models, so the published interface cannot drift from the code. |
| Fixed rules read free text; code decides every price, quantity, allergen status and verdict | Both can be tested and audited, and a text the rules cannot read becomes a question instead of a guess. |
| Policy as YAML: fixed rules plus one profile per buyer | The guardrails can be read and changed without touching code; the policy hash in each event shows which version applied. |
| REST and MCP over one service object | Any agent can use the gateway, by OpenAPI or by MCP, and the rules live in one place. |
| Bearer tokens; the profile comes from the token | An agent cannot choose its own authority. |
| Audit events in a CloudEvents 1.0 envelope, hash-chained | A documented open envelope, and a log that shows tampering. |
| Errors as RFC 9457 problem details; `Idempotency-Key` on orders | Agents branch on a stable error type, and a retry never places a second order. |
| Offers and orders signed by the gateway, key published as a JWK set | A buyer can check a record was not changed after it was issued. The key is a demo key unless the operator sets one. |
| SQLite behind a repository interface; PostgreSQL behind the same interface when `DATABASE_URL` is set | SQLite needs no service. In PostgreSQL the database itself refuses changes to audit events, and the supplier's view is defined in SQL. The supplier view written tonight was not run against a database (`docs/AIVEN.md`). |
| Replay with a pinned clock | The demo gives the same answer at any hour and survives the mock being down. |
| Server-rendered pages and a static shop page, no external asset | One process, no build step, nothing loaded from elsewhere. |

## Out of scope, and not built

- Sending an order to Valio: there is nowhere to send it.
- Payment, and agentic payment standards.
- A signature by Valio Aimo on price, stock or origin: the gateway signs its own records only.
- A model reading requests or photos on the public link: the fixed rules read text; the model code is an option that was not run tonight.
- A "new" or "seasonal" product suggestion: the data has no such mark, so Valio Aimo's own suggestion is a related product.
- Delivery split across dates: the mock cannot show it.
- A fresh offer built automatically when stock runs out while an order waits for approval: the order keeps waiting and the approver picks another option or rejects.
- Deleting a standing order.
- A login: the demo identities and their public tokens stand in for one.
- The shop page was checked by driving its code against a local gateway; nobody on the team has yet signed off its layout in a real browser.

## Next steps toward production

The standards each step would use are in `docs/STANDARDS.md`.
1. An order message Valio's systems can take, in an open e-procurement format such as Peppol BIS Ordering, and Valio's answer on what an accepted order commits to.
2. Valio signing its own statements of price, stock and origin (a Verifiable Credential is one form), so the trust protocol rests on the supplier's signature and not on this gateway's.
3. Real customers, limits, approvers and order history in place of the four synthetic files; the suggestion thresholds set on real orders.
4. A dietitian or a biomedical reviewer signing the formula tolerances, the fat-source word list, the dietary-claim list and the flavour and use word lists.
5. A flavour, a use and a launch or season mark in the product data, so none of them is read from names.
6. OAuth-issued tokens, a login for the pages, and a Host check on the MCP endpoint.
7. The audit head held by another party: run the scheduled witness, and hand the head to buyer and Valio with each order; one canonical JSON form (RFC 8785) for the chain as for the signatures.
8. Run the PostgreSQL proof and the live tests of the supplier view against a database, then a runtime login that does not own the tables.
9. More than one process: a rate limiter and a call budget shared between them.
10. The buyer's needed-by date passed to Valio's `requestedDate`, once the API honours it.
11. A fresh offer when the re-check at approval time fails; a delete route for standing orders.
12. A model as a second reader for the sentences the rules ask about, measured against the same reading table before it is switched on.
