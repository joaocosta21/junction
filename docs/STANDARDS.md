# Open standards, and the path to production

The brief asks for "open, documented standards rather than a proprietary format". This page lists each standard the gateway uses, where in the code, why, where our use departs from it, and what a first pilot would still need.

**RFC numbers cited from the implementers' knowledge; verify against rfc-editor.org before relying on them.** The build had no web access, so no sentence here quotes a specification. Each "Where" below says what the code does, checked on Sat 14 Nov 2026 against commit `c2106fe` by running the gateway offline in replay and by the tests named in each section; the counts and the claims about approval, the audit trail and the signatures were checked again on Sun 15 Nov 2026 against commit `94b21a5`, the same way. Nothing on this page was checked against a deployed copy.

## Summary

| Standard | Where we use it | Status of our use |
|---|---|---|
| OpenAPI 3.1 | `GET /openapi.json`, generated from the typed models | Generated; 27 paths; examples made by running the demo scenarios |
| JSON Schema 2020-12 | `GET /v1/schemas`: 98 models, each with `$schema`; MCP tool schemas | Generated by Pydantic |
| RFC 9457 Problem Details | Every error, over REST and inside MCP tool errors | In use; type URIs are placeholders |
| RFC 9727 API catalog, as an RFC 9264 linkset | `GET /.well-known/api-catalog` | In use; no token needed |
| llms.txt (a community proposal, not a standard) | `GET /llms.txt` | In use |
| RFC 9110 `Location` | The `201` of a new offer, order and standing order | In use |
| Idempotency-Key header (IETF Internet-Draft, version 08) | `POST /v1/orders` | In use; the draft is not an RFC |
| Model Context Protocol, revision 2026-07-28, Streamable HTTP | `/mcp/`, 13 tools, none approves | In use; `Origin` checked, Host not checked, no OAuth |
| RFC 6750 Bearer tokens | Identity on REST and MCP | In use; tokens issued outside OAuth |
| JSON Web Signature (RFC 7515, detached), EdDSA over Ed25519 (RFC 8037), RFC 8785 canonical JSON, JSON Web Key set (RFC 7517), key thumbprint (RFC 7638) | `proof` on every offer and order record; `GET /.well-known/jwks.json` | In use; signed by the gateway, not by Valio Aimo; a demo key unless `TTA_SIGNING_KEY` is set |
| CloudEvents 1.0 | The envelope every audit event is stored in | In use for storage only: `GET /v1/audit` answers a reader's view of each event, not the envelope; the `type` prefix is not reverse-DNS |
| GS1 allergen code lists T4078 and T4079 | Allergen codes and their relations | In use; Valio to confirm its data follows them |
| ISO 4217 currency codes | `EUR` on every amount | In use |
| RFC 3339 timestamps | Every timestamp, with its offset | In use |

Nothing is published for a protocol we do not implement: no UCP profile, no A2A agent card, no MCP server card, no OAuth resource metadata, no AP2 mandate, no Verifiable Credential (`src/tta/api/discovery.py`, `src/tta/api/signing.py`).

## OpenAPI 3.1

**Where.** `GET /openapi.json` is generated by FastAPI 0.162 from the same Pydantic models the code runs on; the document says `openapi: 3.1.0` and holds 27 paths with 29 operations (counted from the running gateway). Each route lists the problem types it can return. The bearer scheme lists the demonstration tokens. The examples in the document are produced by running demo scenarios through the service against the recording; none is written by hand (`src/tta/api/examples.py`). `/docs` shows the document in Swagger UI and `/redoc` in ReDoc.

**Why.** The published interface cannot drift from the code: they are the same models. Any agent framework that reads OpenAPI can call the gateway without our code.

**Assumptions and next steps.** `/docs` and `/redoc` load Swagger UI 5.32.15 and ReDoc 2.5.4 from jsDelivr, each file pinned by version and by its SHA-384 subresource-integrity hash (`src/tta/api/docs_pages.py`). So those two pages need the network. `/openapi.json` does not.

**Checked by.** `tests/api/test_openapi_and_schemas.py`, `tests/api/test_conformance.py`.

## JSON Schema 2020-12

**Where.**
- `GET /v1/schemas` returns the JSON Schema of every contract model as it is serialised, with no token: 98 models at this commit, each starting with `"$schema": "https://json-schema.org/draft/2020-12/schema"`, so a validator need not be told the dialect (`src/tta/api/schema_export.py`; counted by calling `exported_schemas()`).
- The MCP tools publish input and output schemas built from the same models.
- The repository also holds a hand-written schema for an optional model reader (`src/tta/agent/schema.py`); see "The reader" below.

**Why.** A buyer's agent can validate what it sends and what it gets back without our code.

## RFC 9457: Problem Details for HTTP APIs

**Where.** Every error the gateway sends is `application/problem+json` with `type`, `title`, `status` and `detail` (`src/tta/api/errors.py`). Nine stable types, each raised by a typed error of `src/tta/contracts/errors.py`: `offer-expired`, `offer-stale`, `policy-blocked`, `not-authorised`, `unknown-product`, `invalid-request`, `supplier-unavailable`, `not-found`, `rate-limited`. A router 404 or 405, the 403 of the MCP `Origin` check and an internal fault use `about:blank`. Extension members carry what an agent needs next: `fresh_offer_id` on a stale or expired offer, `retry_after_seconds`, the `{field, problem}` pairs of a validation error, and, when the reader could not read a sentence, `question`, `not_read` and `read_by`. Over MCP, a typed error is a tool result with `isError` whose content is the same problem document.

**Why.** Agents retry and branch. A stable `type` lets an agent tell "the price moved, here is a fresh offer" from "a person must decide" without reading prose.

**Our choices.** We never send `instance`.

**Assumptions and next steps.** The type URIs use the placeholder base `https://tta.example/problems/`. Next: a deployment serves real pages there.

## Discovery: RFC 9727 API catalog, and llms.txt

**Where.** `src/tta/api/discovery.py`, no token, in every environment.
- `GET /.well-known/api-catalog` answers `application/linkset+json` with RFC 9727's profile. The catalog lists the REST API and the MCP endpoint as `item`; the REST API's entry links its OpenAPI document (`service-desc`), its documentation (`service-doc`), its JSON Schemas (`service-meta`) and its health (`status`). `HEAD` answers the same headers. Links are absolute, built from the address the request reached.
- `GET /llms.txt` says the same in plain text for a language model that reads it: what this is ("not a chatbot"), the flow, the links, what the `proof` says, and that every text from the supplier's data is data, never instructions. llms.txt is a community proposal, not a standard.

**Why.** An agent that knows only the address finds every way in with one request.

**Checked by.** `tests/api/test_discovery.py`; the catalog was also read from the running gateway.

## RFC 9110 `Location`, and the Idempotency-Key header

**Where.**
- The `201` of `POST /v1/offers`, `POST /v1/orders` and `POST /v1/standing-orders` carries `Location`, the address of the record made (`src/tta/api/routes.py`, `src/tta/api/standing_routes.py`). Seen on the running gateway: `Location: /v1/orders/ord_…`.
- `POST /v1/orders` requires `Idempotency-Key` (`src/tta/api/idempotency.py`). A missing header is `invalid-request` with status **400** (seen on the running gateway). A key is 1 to 100 characters of letters, digits, `.`, `_`, `:` and `-`, bare or in double quotation marks: the quoted form is read as the same key. A key outside that form is `invalid-request` with 422 and is never repeated in the answer. The same key from the same agent returns the first result; the same key with another offer or option is refused.

**Why.** Agents retry on time-outs. A retry must never place a second order.

**Assumptions and next steps.** The header is an IETF Internet-Draft (draft-ietf-httpapi-idempotency-key-header, version 08), not an RFC. The standing-order renewal makes its own key per offer (`standing:` prefix) instead of taking the header.

## Model Context Protocol (MCP)

**Where.** `/mcp/` (`src/tta/api/mcp_surface.py`), built on the official Python SDK `mcp` 2.3.0, Streamable HTTP, POST only: `GET` answers 405 with `Allow: POST`. Thirteen tools, listed from the running gateway:

| Tool | What it does |
|---|---|
| `get_authority` | What the caller's agent may decide alone, and every rule in words |
| `search_products`, `get_product` | Catalog lookup; with `price_and_availability` true, each product also carries the supplier's fixed price and what its data says is available (at most 20 products a call), as the REST routes do |
| `find_substitutes` | Candidates for a product, each judged by the buyer's own rules |
| `get_offer` | A typed request becomes an offer at fixed prices |
| `place_order` | Places the order within the buyer's authority, or sends it to a person |
| `get_order`, `get_audit` | The order record; the audit trail in the caller's view |
| `get_customer` | Who the token's customer is: its people, usual products and history (synthetic) |
| `plan_menu` | A menu (dishes and servings) becomes one offer |
| `set_up_standing_order`, `renew_standing_order`, `list_standing_orders` | Standing orders |

Each tool is one call of the same service the REST routes call, as the identity of the request's bearer token. The server keeps no session and answers in plain JSON. An argument a tool does not know is refused with a problem document, as REST refuses an unknown field.

**Our choice.** **No tool lists or decides an approval.** Approving is done by a person, on the pages or over REST with a person's token; over REST an agent's token is refused with 403 and the attempt is logged (rule F-06: an agent can never approve an order, its own included). That guarantee is one of REST and MCP, where a token says who calls. The demonstration pages take no credential (see "RFC 6750" below).

**The `Origin` check.** A request that carries an `Origin` header the server does not allow is answered **403** with a problem document, before the token is looked at (`src/tta/api/mcp_origin.py`; seen on the running gateway with `Origin: https://evil.example`). Allowed: pages on the machine itself (`localhost`, `127.0.0.1`, `[::1]`, any port) and the origins of the setting `TTA_MCP_ALLOWED_ORIGINS`. A request with no `Origin`, from an agent or a program, is served.

**Where we depart.**
- **The Host header is not checked.** The SDK's own Host-and-Origin check is switched off, because the gateway is served behind a proxy that sets Host; a request with another Host was served in our run. A deployment that knows its public address should check it.
- **No OAuth.** Tokens are handed out outside the protocol, and the server publishes no OAuth protected-resource metadata. A host that expects the OAuth flow will not find one.
- Not tried with a third-party MCP host such as Claude Desktop or MCP Inspector: the tests use the SDK's own client.

**Checked by.** `tests/mcp/test_tools.py`, `tests/mcp/test_origin.py`, `tests/mcp/test_methods.py`, `tests/mcp/test_approval.py`.

## RFC 6750: Bearer Token Usage

**Where.** Every call to `/v1` except `/v1/schemas`, and every MCP request. One token maps to one identity: an agent bound to one buyer profile, an approver with roles, or the supplier reader. Tokens are kept as SHA-256 digests (`src/tta/api/identity.py`). REST answers a missing or unknown token with 401, `WWW-Authenticate: Bearer` and a problem document; MCP answers 401 with `WWW-Authenticate: Bearer error="invalid_token"` (both seen on the running gateway).

**Why.** The buyer profile, and so the agent's authority, comes from the token, never from a request field. An agent cannot choose its own limits. Valio Aimo's token reads its view of the audit trail and nothing else: `GET /v1/customers` answers it 403.

**Assumptions and next steps.** Tokens come from `TTA_TOKENS`, not from an authorization server. The 11 demonstration identities in `src/tta/api/demo_tokens.yaml` (4 agents, 6 approvers, Valio Aimo's reader) are public by design and load only when `TTA_ENV` is `dev` or `demo`. **The demonstration pages (`/shop` and the older pages) use no token and have no login:** a page acts as the customer's person it shows, in an order book per browser, so whoever opens it can confirm as any of that customer's people. The pages are mounted only in `dev` and `demo`; anywhere else no page exists and a person decides with a token of their own.

## Signed offers and order records

**Where.** `src/tta/api/signing.py`, `src/tta/api/keys.py`. Every offer and every order record that a REST route or an MCP tool answers carries `proof`: a detached JSON Web Signature, algorithm EdDSA over Ed25519, over the record without `proof`, written as RFC 8785 canonical JSON. The public key is a JSON Web Key set at `GET /.well-known/jwks.json`, no token needed; its `kid` is the key's thumbprint. `GET /healthz` names the key and says whether it is a demo key.

**How to check a record.** Take the JSON as answered, remove `proof`, write the rest as RFC 8785 says, and verify `<header>.<base64url of those bytes>` against the signature, where `proof.jws` is `<header>..<signature>`. A changed price, quantity, verdict or name no longer verifies.

**What is signed.** The offer answered by `POST /v1/offers`, `GET /v1/offers/{id}` and the tool `get_offer`; the order record answered when it is placed, read, listed or decided; the offer and the order inside a standing-order renewal.

**What is not signed.**
- **Nothing is signed by Valio Aimo.** The signature says that this gateway answered this record, and no more. It is not a statement by the supplier about price, stock or origin, and it is not a Verifiable Credential.
- With no `TTA_SIGNING_KEY` set, the key is a **demo key** generated when the gateway starts and gone at the next start. Every proof then says `demo_key: true`, and nothing is claimed about such a signature beyond that run.
- Audit events are hash-chained, not signed (next section). Stored records and the audit trail hold no proof: the proof is made when a record is answered. So **a stored order or offer is not protected by it.** Whoever can write the database can change a stored order, and the gateway then answers the changed order with a proof that verifies (a security check on 15 Nov changed a stored total from 1,083.39 to 1.39 and got one), while the audit chain stays intact. Tying each record to its audit event is a next step.
- `demo_key` and the kind of record (`typ`) are inside the signed protected header. `proof.demo_key` and `proof.note`, beside the signature, repeat them and are not covered by it: read the header.
- Product lookups, search results, the customers route and the menu-plan answer carry no proof.
- No payment is taken or signed: every order's `record_note` says so.

**Why.** It answers the brief's "trust protocol" for the one party we can speak for: a buyer can later show what the gateway told its agent, using nothing but the published key.

**Checked by.** `tests/api/test_signing.py` (RFC 8785's own example, numbers written as ECMAScript writes them, an offer that fails on a changed price, a key that is not an Ed25519 seed stops the start).

## CloudEvents 1.0

**Where.** Every audit event is stored in this envelope (`src/tta/contracts/audit.py`, `src/tta/audit/trail.py`): `specversion` `1.0`, a fresh `id`, `source` `/tta/gateway`, a `type` such as `tta.v1.offer.created`, `tta.v1.approval.decided` or `tta.v1.settings.changed` (20 types), `time`, `subject`, `datacontenttype` `application/json`, and `data`. Inside `data` we add, as our own design: the actor, rule ids, facts, the policy hash, one readable sentence written from a template, the previous event's hash and the event's own SHA-256 hash.

**Why.** A documented open envelope for the stored trail. The hash chain on top shows an event that was changed, inserted, or removed from anywhere but the end.

**Where we depart.**
- **The interface does not answer CloudEvents.** `GET /v1/audit` and the tool `get_audit` answer a reader's view of each event (`id`, `type`, `time`, `actor`, `sentence`, `rule_ids`, `facts`, `hash`; no `specversion`, `source`, `subject` or `data`), because the buyer and Valio Aimo each see their own projection. So the trail as answered cannot be loaded into a tool that reads CloudEvents, and a reader cannot recompute an event's hash from its view (the facts are masked): `chain.ok` and `/healthz` are the gateway's own verification. Answering the envelope is a next step.
- The `type` prefix is `tta.v1.`, not a reverse-DNS name: the project owns no domain.
- `source` is a relative URI-reference.
- The event hash is SHA-256 over the event's JSON with sorted keys and no spaces (`src/tta/audit/chain.py`). It is **not** RFC 8785 canonical JSON, unlike the signatures above, so another implementation could write a number differently and get another hash.
- The chain uses no key and nobody else holds its head: whoever can write the database can rewrite the end of the trail. `/healthz` publishes the head (event count and last hash) and verifies the whole chain of the shared order book for its answer, at most once every 30 seconds: a changed, inserted or removed event makes it answer `degraded` and name the first event that does not verify. Nobody outside the gateway holds the head yet.

## GS1 allergen code lists

**Where.** Allergen exclusions on a request and in a buyer profile are GS1 allergen type codes (code list T4078), for example `AM` milk, `AW` cereals containing gluten, `AN` tree nuts, `AP` peanuts, `AS` sesame; an unknown code is `invalid-request`. The product file's statements are read with the levels of containment of code list T4079: `CONTAINS`, `MAY_CONTAIN`, `FREE_FROM`, `UNDECLARED` (`src/tta/allergens/codes.py`, `src/tta/allergens/exclusion.py`). `X99` ("Does not contain declaration obligatory allergens") is read as a general statement, never a statement about one allergen. The product file uses 45 codes, all in our table (whole catalog, 17,546 products; pinned by `tests/allergens/test_codes.py`).

**Why.** The codes are already in Valio's data, and they are the codes food-service systems exchange. A buyer's agent can state "no milk, no gluten" without our vocabulary.

**Assumptions and next steps.**
- Which member codes belong to a family (for example `AW` → wheat, rye, barley, oats, spelt, kamut) is our reading.
- We read Valio's data as following the GS1 lists. Valio has not confirmed it.
- A nutritional claim is never an allergen statement (lactose-free milk still declares milk), and no data means unknown, not safe.
- The code names in our table were typed from the GS1 lists by the build; they were not re-read at the source for this page.

## ISO 4217 and RFC 3339

**Where.** Every amount carries `currency: "EUR"` (`src/tta/contracts/common.py`); money is computed with `Decimal`. Every timestamp the gateway sends has an offset: Valio's times keep the offset Valio sent (Helsinki, `+02:00` in November); audit event times are in UTC.

## Who reads a sentence: a model, a recording, the fixed rules

This is a choice, not a standard, and it shapes everything above. A request arrives typed (`POST /v1/offers`, the tool `get_offer`) or as a sentence (`POST /v1/requests/parse`). A model reads the sentence first when one is configured (`GEMINI_API_KEY`, or an OpenAI-compatible endpoint by the `TTA_AGENT_*` settings); the gateway checks its reading against the text and refuses one that does not match, never correcting it. When no model answers, or none is configured, a sentence is answered from a labelled recording when the repository holds one for that sentence and that buyer (11 files in `fixtures/agent/`; over REST and MCP with the demonstration tokens that is the case for the sentences of scenarios 1 and 2), and otherwise read by **fixed rules** (`src/tta/agent/rules_reader.py`). On `/shop` no recording is served, because a page's order book carries a profile of its own. What the rules cannot read is not guessed: the answer is `invalid-request` (422) with a question for the person (seen on the running gateway: "How much is needed, and of what? For example: 200 litres of oat drink by Monday."). Every reading says who read it, in the headers `TTA-Read-By`, `TTA-Reading-Source` and `TTA-Reading-Sentence`.

So the fixed rules are the model's check and its fallback, not a replacement for it. Measured by the build on 15 Nov with a key set, on a local gateway: the brief's own sentence was read by `gemini-3.6-flash` (`TTA-Read-By: gemini-3.6-flash`, `TTA-Reading-Source: model`); a reading whose day did not match the text was refused; and when the model answered 429 twice the fixed rules read the sentence and said so. The tests call no model, and we do not enter Google's award. `GET /healthz` → `agent_reader` says what reads sentences on a given gateway; a deployer who wants no model sets no key. A model proposes a reading; it never decides a price, a quantity, an allergen status or a verdict.

## Next steps toward production

Ordered by what a first real pilot would need.

1. **An order message Valio's systems can take.** Today "ordered" means recorded in our order book: the mock has no order endpoint, by design, and the record commits nobody. The order record keeps the lines, the prices with their validity, and the stock and delivery statements it relied on. Next: map it to an open e-procurement format such as Peppol BIS Ordering (a UBL order). Not started.
2. **Statements signed by the supplier.** Today the gateway signs what it answered. The next step for the brief's "trust protocol" is for Valio Aimo to sign its own statements of price, stock and origin, for example as W3C Verifiable Credentials, so that the status "confirmed" rests on the supplier's key and not on our reading of its API. A proposal; nothing of it is built.
3. **A fixed signing key, and a key history.** Set `TTA_SIGNING_KEY` from a secret store; keep retired public keys in the key set so an old record still verifies.
4. **Real customers.** The four customers, their people, limits and order history are ours and synthetic. Next: profiles per customer, approvers from the customer's own identity system, the order history from Valio.
5. **Authorisation on the agent surfaces.** Check Host on `/mcp/` against the public address; issue tokens through OAuth with protected-resource metadata instead of `TTA_TOKENS`; a login before the pages leave `dev` and `demo` (today they have none); a second signer above an amount where one person now holds every role.
6. **An audit trail the other party can check.** Answer the trail as CloudEvents at the interface; tie each stored order and offer to its audit event, so a record changed in the database no longer gets a valid proof; hash events as RFC 8785 canonical JSON, as the signatures already do; hand the head of the chain to the buyer and to Valio with each order, so a cut-off end shows. A scheduled witness of the head exists as code (`deploy/witness.py`) and has not run.
7. **Payment.** None is taken. The record assumes a credit customer invoiced after delivery for what is delivered. An agentic payment standard would attach here, to the signed order record.
8. **More than one process.** The order book's lock, the rate limiter and the pages' own books are in one process's memory.
9. **Pass the buyer's date to Valio.** The client sends today's date as `requestedDate`, which the mock ignores; the needed-by date is checked in our code.
10. **Owned names.** Serve the problem-type pages at a real address; replace the `tta.v1.` event prefix with a reverse-DNS name the operator owns.
11. **A fresh offer when stock runs out while an order waits for a person.** Today the re-check blocks the order (rule F-04: an option that expired or changed cannot be ordered) and the approver picks another option or rejects.
