# Open standards, and the path to production

The brief asks for "open, documented standards rather than a proprietary format". This page lists each standard the gateway uses, where, and why. Every statement about a standard was checked on 14 Nov 2026 against the specification page linked in its section. Where our use departs from the standard, the section says so.

## Summary

| Standard | Where we use it | Status of our use |
|---|---|---|
| [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0) | `GET /openapi.json`, generated from the typed models | Generated, with examples from real runs |
| [JSON Schema 2020-12](https://json-schema.org/draft/2020-12) | `GET /v1/schemas`; MCP tool schemas; the model's answer schema | Generated by Pydantic; the model's schema is hand-written |
| [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) | Every error, over REST and inside MCP tool errors | In use; type URIs are placeholders |

## OpenAPI 3.1

**What the standard is.** "The OpenAPI Specification (OAS) defines a standard, programming language-agnostic interface description for HTTP APIs." Its Schema Object "is a superset of JSON Schema Specification Draft 2020-12". A security scheme of type `http` names an HTTP authorization scheme such as `bearer`. Source: [spec.openapis.org/oas/v3.1.0](https://spec.openapis.org/oas/v3.1.0).

**Where.** `GET /openapi.json` is generated by FastAPI 0.162 from the same Pydantic models the code runs on; FastAPI's default `openapi_version` is `3.1.0`. Each route lists the problem types it can return; only the 413 for a body over 64 KB is described in the document's text instead. The bearer scheme comes from FastAPI's `HTTPBearer`. The examples in the document are produced by running scenarios 1, 2 and 3 through the service against the recorded capture; none is written by hand (`src/tta/api/examples.py`). `/docs` shows the document in Swagger UI and `/redoc` in ReDoc.

**Why.** The published interface cannot drift from the code: they are the same models. Any agent framework that reads OpenAPI can call the gateway without our code.

**Limits.** `/docs` and `/redoc` load Swagger UI 5.32.15 and ReDoc 2.5.4 from jsDelivr, pinned, each file checked by its SHA-384 subresource-integrity hash, under a Content-Security-Policy that allows only that CDN (`src/tta/api/docs_pages.py`, task FIX-10). So they need the network. `/openapi.json` does not.

## JSON Schema 2020-12

**What the standard is.** Draft 2020-12 "is a comprehensive update to the previous draft 2019-09". Its meta-schema is `https://json-schema.org/draft/2020-12/schema`. Source: [json-schema.org/draft/2020-12](https://json-schema.org/draft/2020-12).

**Where.**
- `GET /v1/schemas` returns the JSON Schema of every contract model, as it is serialised, with no token needed (`src/tta/contracts/schemas.py`). Pydantic v2 writes these in the 2020-12 dialect (its `GenerateJsonSchema.schema_dialect`).
- The MCP tools publish input and output schemas built from the same models. The MCP specification says tool schemas default to 2020-12 when no `$schema` is given ([tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)).
- The schema Gemini fills when it reads a request is written by hand (`src/tta/agent/schema.py`). It follows the request contract field by field, and a test compares the two. It leaves out keywords such as long patterns and `maxItems` 1000, which a model API may ignore or refuse.

**Why.** A buyer's agent can validate what it sends and what it gets back without our code.

## RFC 9457 — Problem Details for HTTP APIs

**What the standard is.** Errors as JSON with the media type `application/problem+json` and the members `type`, `status`, `title`, `detail` and `instance`. When `type` is absent it is `about:blank`, which "indicates that the problem has no additional semantics beyond that of the HTTP status code". A problem type "MAY extend the problem details object with additional members". RFC 9457 obsoletes RFC 7807. Source: [rfc-editor.org/rfc/rfc9457](https://www.rfc-editor.org/rfc/rfc9457).

**Where.** Every error the gateway sends (`src/tta/api/errors.py`). Nine stable types, each raised by a typed error of `src/tta/contracts/errors.py`: `offer-expired`, `offer-stale`, `policy-blocked`, `not-authorised`, `unknown-product`, `invalid-request`, `supplier-unavailable`, `not-found`, `rate-limited`. Router 404 and 405 and an internal fault use `about:blank`. Extension members carry what an agent needs next: `fresh_offer_id` on a stale or expired offer, `retry_after_seconds`, the `{field, problem}` pairs of a validation error. Over MCP, a typed error is a tool result with `isError` whose content is the same problem document.

**Why.** Agents retry and branch. A stable `type` lets an agent tell "the price moved, here is a fresh offer" from "a human must decide" without reading prose.

**Our choices.** We never send `instance`, and no problem repeats text the caller sent: both could echo input back.

**Limits.** The type URIs use the placeholder base `https://tta.example/problems/`. A deployment must serve real pages there.

## CloudEvents 1.0

**What the standard is.** An event envelope. REQUIRED attributes: `id`, `source`, `specversion`, `type`. OPTIONAL: `datacontenttype`, `dataschema`, `subject`, `time`. Producers "MUST use a value of `1.0`" for `specversion`. `source` is a non-empty URI-reference; an absolute URI is RECOMMENDED. `type` "SHOULD be prefixed with a reverse-DNS name". `time` "MUST adhere to the format specified in RFC 3339". Source: [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md).

**Where.** Every audit event (`src/tta/contracts/audit.py`, `src/tta/audit/trail.py`): `specversion` `1.0`, a fresh `id`, `source` `/tta/gateway`, `type` such as `tta.v1.offer.created` or `tta.v1.approval.decided`, `time`, `subject` (`order/<id>`, `offer/<id>` or `approval/<id>`), `datacontenttype` `application/json`, and `data`. Inside `data` we add, as our own design: the actor, rule ids, facts, the policy hash, one readable sentence, the previous event's hash and the event's own SHA-256 hash.

**Why.** A buyer or Valio Aimo can load the trail into any tool that reads CloudEvents. The hash chain on top shows an event that was changed, removed or inserted.

**Where we depart.**
- The `type` prefix is `tta.v1.`, not a reverse-DNS name: the project owns no domain. A deployment replaces it with its own.
- `source` is a relative URI-reference. That is allowed; an absolute URI is recommended.
- The event hash is SHA-256 over the event's JSON with sorted keys and no spaces. It is not [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) canonical JSON (an Informational RFC), so another implementation could serialise a number differently and get another hash.

## Model Context Protocol (MCP)

**What the standard is.** MCP lets servers "expose tools that can be invoked by language models". Clients list tools with `tools/list` and call them with `tools/call`. A tool has an `inputSchema` and may have an `outputSchema`; results may carry `structuredContent`; a tool execution error is a result with `isError: true` ([tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). The Streamable HTTP transport uses one MCP endpoint for POST and GET, and a server may answer a request with `Content-Type: application/json` ([transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)). Authorization "is OPTIONAL for MCP implementations"; when an HTTP server supports it, it SHOULD follow the OAuth 2.1-based flow, and the client sends `Authorization: Bearer <access-token>` on every request ([authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). The current revision is [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28).

**Where.** `/mcp/` (`src/tta/api/mcp_surface.py`), built on the official Python SDK `mcp` 2.3.0. Eight tools: `get_authority`, `search_products`, `get_product`, `find_substitutes`, `get_offer`, `place_order`, `get_order`, `get_audit`. Each tool is one call of the same service the REST routes call, as the identity of the request's bearer token. No logic lives in the transport. The server keeps no session and answers in plain JSON, so any replica can answer. `GET` and `DELETE` on `/mcp` and `/mcp/` answer 405 with `Allow: POST`: the server offers no event stream. The build checked the surface with the SDK's own client in protocol versions 2026-07-28 and 2025-11-25 (`AIMO/build/handback/T11.md`).

**Why.** An agent host that speaks MCP can use the wholesaler with no custom code. The brief leaves open whether the production interface is "a traditional API, an MCP-style agentic interface or a full service agent"; we offer both REST and MCP over one service.

**Our choice.** There is no tool that lists or decides an approval. Approving is done by a human, on the pages or over REST.

**Where we depart.**
- **No OAuth.** Tokens are handed out outside the protocol, and the server publishes no OAuth protected-resource metadata. The specification allows this, since authorization is optional, but a host that expects the OAuth flow will not find one.
- **The `Origin` header is not checked.** The transport page says servers "MUST validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks". We turned off the SDK's Host and Origin check, because its default accepts only `localhost` and no setting holds the public address yet. This is the first item to close before production (next steps, item 3).
- Not yet tried with a third-party MCP host such as Claude Desktop or MCP Inspector.

## RFC 6750 — Bearer Token Usage

**What the standard is.** "The OAuth 2.0 Authorization Framework: Bearer Token Usage". A client sends `Authorization: Bearer <token>`. For a token that is "expired, revoked, malformed, or invalid for other reasons", the resource server answers 401 with a `WWW-Authenticate` header carrying `error="invalid_token"`. Source: [rfc-editor.org/rfc/rfc6750](https://www.rfc-editor.org/rfc/rfc6750).

**Where.** Every call to `/v1` except `/v1/schemas`, and every MCP request. One token maps to one identity: an agent bound to one buyer profile, an approver with roles, or the supplier reader. Tokens are kept as SHA-256 digests and compared in constant time (`src/tta/api/identity.py`). REST answers a missing or unknown token with 401, `WWW-Authenticate: Bearer` and a problem document. MCP answers with the SDK's 401 and `WWW-Authenticate: Bearer error="invalid_token"`.

**Why.** The buyer profile, and so the agent's authority, comes from the token, never from a request field. An agent cannot choose its own limits.

**Limits.** Tokens come from `TTA_TOKENS`, not from an authorization server. The demo tokens in `src/tta/api/demo_tokens.yaml` are public by design and load only when `TTA_ENV` is `dev` or `demo`.

## GS1 allergen code lists

**What the standard is.** GS1 code list T4078 "Allergen type code" names each allergen. For example `AM` "Milk and its derivatives", `AW` "Cereals and its derivatives" (cereal grains containing gluten), `GO` "Oats and its derivatives", `UW` "Wheat and its derivatives", `ML` "Lactose", and `X99` "Does not contain declaration obligatory allergens in the product." Code list T4079 "Level of containment code" gives the relations, among them `CONTAINS` ("Intentionally included in the product"), `MAY_CONTAIN`, `FREE_FROM` ("The product is free from the indicated substance") and `UNDECLARED` ("Not intentionally included in the product and assessed not to require a cross-contact declaration"). Sources: GS1 Sweden's pages for [T4078](https://gs1.se/en/guides/documentation/code-lists/t4078-allergen-type-code/) and [T4079](https://gs1.se/en/guides/documentation/code-lists/t4079-level-of-containment-code/).

**Where.** Allergen exclusions on a request and in a buyer profile are GS1 codes; an unknown code is `invalid-request`. The product file's statements are read with these meanings (`src/tta/allergens/codes.py`, `src/tta/allergens/exclusion.py`). `X99` is read as GS1 defines it: a general statement, never a statement about one allergen. The product file uses 45 codes, all in our table (whole catalog).

**Why.** The codes are already in Valio's data, and they are the codes food-service systems exchange. A buyer's agent can state "no milk, no gluten" without our vocabulary.

**Limits.**
- Which member codes belong to a family (for example `AW` → wheat, rye, barley, oats, spelt, kamut) is our reading, written in `src/tta/allergens/codes.py`.
- We read Valio's data as following the GS1 lists. Valio has not confirmed it (`AIMO/BOOTH-QUESTIONS.md`, Q2).
- Only the declaration is read today. The product's own ingredient list is being added as a statement (task FIX-12a): `465793` declares tree nuts free from while its ingredients name almond (question ALMOND-1). <!-- check: FIX-12a -->
- The code names in our table were read from T4078 on 14 Nov. Eight match the names our data notes quote; the other 37 have not been spot-checked one by one.

## ISO 4217 currency codes

**What the standard is.** ISO 4217 defines currency codes, `EUR` among them. SIX "is the official Maintenance Agency of these currency codes under ISO 4217" and publishes the current list ([SIX data standards](https://www.six-group.com/en/products-services/financial-information/data-standards.html)).

**Where.** Every amount in an offer and an order carries `currency: "EUR"` (`src/tta/contracts/common.py`). A price from Valio in any other currency makes the product `PRICE_UNAVAILABLE`. Money is computed with `Decimal` and sent as a JSON number with two decimals.

## RFC 3339 and ISO 8601 timestamps

**What the standard is.** RFC 3339, "Date and Time on the Internet: Timestamps", is "a profile of the ISO 8601 standard". A timestamp ends with `Z` or a numeric offset such as `+02:00`. Source: [rfc-editor.org/rfc/rfc3339](https://www.rfc-editor.org/rfc/rfc3339).

**Where.** Every timestamp the gateway sends has an offset. Valio's times keep the offset Valio sent (Helsinki, `+02:00` in November). Audit event times are in UTC. CloudEvents requires RFC 3339 for `time`, and ours follow it.

## Idempotency-Key header (Internet-Draft)

**What it is.** "The Idempotency-Key HTTP Header Field", an Internet-Draft of the IETF HTTPAPI working group (version 08, 22 October 2026). It is not an RFC yet. Its abstract says the header "can be used to make non-idempotent HTTP methods such as POST or PATCH fault-tolerant". Source: [datatracker.ietf.org](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/).

**Where.** `POST /v1/orders` requires `Idempotency-Key`. The same key from the same agent returns the first result; the same key with another offer or option is `invalid-request`. A key is 1 to 100 characters of letters, digits, `.`, `_`, `:` and `-`.

**Why.** Agents retry on time-outs. A retry must never place a second order.

## Next steps toward production

Ordered by what a first real pilot would need. Each item names where the gap is recorded.

1. **An order message Valio's systems can take.** Today "ordered" means recorded in our order book: the mock has no order endpoint. The order record keeps the lines, the prices with their validity, and the stock and delivery statements it relied on. Next: map it to an open e-procurement format such as [Peppol BIS Ordering 3.3](https://docs.peppol.eu/poacc/upgrade-3/profiles/28-ordering/), which covers "the sending of Orders from a Buyer to a Seller and the response of the Seller" with a binding to OASIS UBL 2.1. What an accepted order commits Valio to is still open (`AIMO/BOOTH-QUESTIONS.md`, Q4).
2. **Real customer limits.** The two buyer profiles and their limits are illustrative and labelled as ours; the mock has no customer model (Q7). Next: profiles per customer, approvers from the customer's own identity system.
3. **Authorisation on the agent surfaces.** Check `Origin` and `Host` on `/mcp/` against a configured public address. Then issue tokens through OAuth 2.1 with protected-resource metadata, as the [MCP authorization page](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) describes, instead of `TTA_TOKENS`. Add a login before the pages leave `dev` and `demo`.
4. **An audit trail the other party can check.** Hash events as RFC 8785 canonical JSON; hand the head of the chain (event count and last hash) to the buyer and to Valio with each order, so a cut-off end shows. PostgreSQL with triggers that refuse changes to audit rows is committed (task S1, `67f3b00`, `docs/AIVEN.md`) and reaches the deployed app at the final redeploy; next, a runtime login that does not own the tables, and a checked server certificate. <!-- check: S1 -->
5. **More than one process.** The order book's lock, the rate limiter and the agent-run log are in one process's memory. Next: a unit of work in the store and a shared limiter.
6. **Pass the buyer's date to Valio.** The client sends today's date as `requestedDate`, which the mock ignores; the needed-by date is checked in our code. A real API that honours the date needs one argument on two port methods (question T01-2).
7. **Signed supplier statements.** The verification status per claim tells an agent what Valio's data confirms. A next step for the brief's "trust protocol" is for Valio to sign those statements, for example as credentials in the [W3C Verifiable Credentials Data Model v2.0](https://www.w3.org/TR/vc-data-model-2.0/) (a W3C Recommendation since 15 May 2025). This is a proposal; nothing of it is built.
8. **Owned names.** Serve the problem-type pages at a real address; replace the `tta.v1.` event prefix with a reverse-DNS name the operator owns.
9. **Delivery and sustainability in the comparison.** Delivery reliability and carbon values are loaded onto each product but not used in ranking or shown on the offer. Valio's data covers 25.2% of products for reliability and 62.9% for carbon (whole catalog, `AIMO/FINDINGS.md`).
10. **Bounded agent runs.** A whole agent run has no deadline, and the model's output length has no cap; with Gemini timing out, the first sentence can wait about 60 seconds before its recording answers (`AIMO/build/handback/FIX-9.md`).
11. **Standing orders.** None is built. Next: a renewal the buyer's agent can ask for, and a rule like P-02 that sends an order to a human when its quantity or unit price drifts from the buyer's recent orders (`AIMO/USE-CASES.md`, use case 6).
