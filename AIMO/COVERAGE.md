## Summary

### The pipeline

One Python process (FastAPI), the "gateway", between a buyer's agent and Valio's mock API. REST (`/v1/*`) and MCP (`/mcp/`, 13 tools) call the same service object (`src/tta/api/service.py`); the pages are a front end to the same functions.

1. **Request.** A typed request (`POST /v1/offers`, MCP `get_offer`): lines with a product type or product ids, quantity, unit, needed-by date, required claims and labels, allergen exclusions, whether the formula matters (`keep_formula`), a preference. Or a sentence (`POST /v1/requests/parse`, `POST /v1/agent/run`, the shop page).
2. **Reading.** A sentence is read by a model when a key is set, its reading checked against the text and refused when it does not match; otherwise from a recording of that sentence, else by the fixed rules. Nothing is guessed: what the rules cannot read comes back as a question (status 422 with the question), not as an offer for something else. Measured by the build on 15 Nov with a key set (not by this refresh): the brief's own sentence was read by `gemini-3.6-flash` into 1,000 L, product type milk, claim `FREE_FROM_LACTOSE`, Monday 16 Nov (`TTA-Read-By: gemini-3.6-flash`, `TTA-Reading-Source: model`); a loosely worded sentence whose day the model got wrong was refused ("the reading did not match the text: the text names another day"); when the model answered HTTP 429 twice, the fixed rules read the sentence and the answer said so. Measured again by the build at 03:40 with a key set: after a first HTTP 429 the model is not asked again for 120 seconds; in that time a sentence the fixed rules can read is read by them, and one they cannot read is answered 503 with the rules' own reason in it ("The language model did not answer … The fixed rules could not read it either: …"). A price named for the whole request is read since commit `fe3ae8c`: an amount named for the whole request ("under €400", "max 1000 euros", "a budget of €1,000") is read into the request (`max_net_eur`, euros before tax) and applied by rule P-01 as a spend limit for that one request, the lower of it and the buyer's own limit per order: it can only tighten, it is not the daily limit and it removes no option. Measured at the demo clock, hotel: "200 litres of lactose-free milk by Monday, under €400" → 200 × `469363` is €496.00 and waits for a person, "The total of €496.00 before tax is above the €400 you named for this request."; with "under €600" and ordering alone on, the agent orders it ("… within the €750 limit per order and the €600 you named for this request …"). With no key: *Run:* "some stuff for the weekend please" → 422, "By which day are the goods needed?". *Run 15 Nov:* on `/shop` "1,000 litres of lactose-free milk by Monday" is read by the fixed rules ("Read by fixed rules, not by a model: no Gemini key is set."); over REST with the hotel's demo token the same sentence is answered from a recording made for that profile, and the headers say so (`TTA-Read-By`, `TTA-Reading-Source`, `TTA-Reading-Sentence`). The result is the same typed request as in step 1. Asked about and never guessed (15 Nov): a minus, cartons and other containers, a price per unit ("a limit on a unit price is not applied"), and a Finnish or Swedish sentence ("the fixed rules read English only for now").
3. **Candidates.** Product types (32, ours), name terms, claims, pack size and lot step from the product file (`src/tta/catalog/`). No call to Valio yet.
4. **Lookup.** One price call and one availability call for the narrowed set (`src/tta/valio/`), from the mock or from the recording, never one of each; one more of each when a short confirmed fill is completed with a substitute (15 Nov). Every run described here used the recording.
5. **Offer.** Each product gets one of six availability states and a status per statement (price, quantity, delivery date, allergens, origin); the buyer's allergen exclusions are applied; at most three options are built, four under a preference (`src/tta/offers/options.py`). Everything left out is listed with a reason. The offer is signed by the gateway (item 13).
6. **Rules.** Each option is judged by rules kept as data (`src/tta/policy/rules.yaml`) with the buyer's own limits (`src/tta/policy/profiles/*.yaml`, four customers). The outcome is: the agent may order (`AUTO`), a named role must sign (`APPROVAL`), or it cannot be ordered (`BLOCK`).
7. **Order prepared.** `POST /v1/orders` with an `Idempotency-Key` (without one: 400). Price and availability are asked again; the rules run again. The order waits (`PENDING_APPROVAL`).
8. **A person confirms** (`POST /v1/approvals/{id}/decision`, the shop page). The check runs once more, then the order is `ORDERED`. An agent's token on this route is refused (403), and MCP has no approval tool. The demo pages have no login: whoever opens `/shop` acts as the customer's person (item 3). **The agent orders alone** only when the buyer switched that setting on, no rule fired and every statement of every line is confirmed. The setting is off in all four shipped profiles, so in the build as shipped no order is placed without a person.
9. **Log.** Every step writes one event with one sentence built from a template, chained by SHA-256 hashes (`src/tta/audit/`). The buyer and Valio Aimo each read their own view (`GET /v1/audit?reader=buyer|supplier`).

"Ordered" means recorded in our order book. The mock has no order endpoint; the order step, its approval and its record are ours to define. Every order record says so, and says that no payment is taken.

## Optional – open directions

### 4. Delivery time & sustainability comparison

> "Delivery time & sustainability comparison: not just price, but delivery reliability and the certificates/sustainability labels already shown in the webshop. (Category-level carbon-footprint ranges are a stretch goal.)"

| | |
|---|---|
| **What we do** | Each offer line shows its delivery reliability, carbon figure and certificate labels from Valio's files. Each option states its earliest and latest delivery, lowest reliability, an estimated carbon total and the labels every line carries. A request may set `prefer` to `EARLIEST`, `RELIABILITY` or `LOWER_CARBON`, and may require labels (for example `EU_ORGANIC_FARMING`). Under a preference the offer adds the cheapest confirmed option and says the difference in euros and what it buys. A preference that costs more than 25% above the cheapest confirmed option comes second, not first, and a known reliability under 90% ranks with an unknown one (both thresholds are ours and are named as ours). A profile may set a lower share (ward and bakery: 10%) above which a person decides: rule P-09, "An option ranked by a preference (most reliable, lowest carbon, earliest) that costs more than … above the cheapest confirmed option goes to the purchasing manager." ### 15. Response logic

## How each step is checked

**How the build was checked** (from `AIMO/build/replan/RUNBOOK.md` and the log in `STATUS.md`). One orchestrating session coordinates; agents build.
