**Context:** the deployment brief says a Volume is mounted for `var/` (database, call budget, recordings). The store opens SQLite in WAL mode. **We did:** mounted the Volume at the data directory (`TTA_DATA_DIR=/data`), so the call budget and the recordings are written straight to it. SQLite runs on the container's own disk (`TTA_DB_PATH=/tmp/tta/tta.sqlite3`). Its copy on the Volume is restored at start and refreshed about a second after each change (SQLite backup API, a one-step replace, then `volume.commit()`), with one more copy at shutdown. **We got:** Modal's docs give no SQLite guidance and say Volumes do not support distributed file locking. SQLite says WAL does not work over a network file system. Modal's only SQLite example builds the database off the Volume and copies it in. Run locally with the image's file layout and environment, the order and its audit chain survived a restart. **Example to show:** `deploy/modal_app.py` (`restore`, `snapshot`, `DatabaseSaver`), `tests/deploy/test_database_copy.py`. **Ask:** "The database lives on local disk with a copy kept on the Volume, instead of the SQLite file sitting on the Volume — is that expected, or did we get the brief wrong?" **If no answer, we build:** as described. Putting SQLite straight on the Volume is a one-line change in `IMAGE_ENV`: drop `TTA_DB_PATH` and stop wrapping the app in `SaveAfterRequests`. It is untested on Modal.
