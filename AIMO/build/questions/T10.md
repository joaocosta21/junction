## 1. For the team — when Gemini is down and a key is set, should the recorded answers take over?
**Context:** With no key the parser and the agent run on the recordings of `fixtures/agent/`. With a key they call Gemini, and when Gemini cannot be reached they answer `supplier-unavailable` (task T10: "a clear `supplier-unavailable` when the model cannot be reached"). **We did:** the live check on 14 Nov, two requests to `gemini-3.8-flash`. **We got:** HTTP 503 both times, so with the key set, pasting scenario 1 at that moment would have shown an error, while the same sentence works with no key. **Example to show:** `POST /v1/requests/parse` with "1,000 litres of lactose-free milk by Monday", once with `GEMINI_API_KEY` set while the API answers 503, once with it unset. **Ask:** "With a key set and Gemini down, the demo sentence fails; with no key it works. Is that expected, or did we get something wrong?" **If no answer, we build:** as it is: no fall-back. A fall-back for the recorded sentences is about ten lines in `tta/agent/__init__.py` (a model that tries Gemini and, on `supplier-unavailable`, serves the recording and labels the run `recorded`).

## 2. For the team — what a trace calls answers that a person wrote
**Context:** `AgentRun.model` is "the model id, or `recorded` when served from recorded outputs" (`tta/contracts/agent.py`). The live check did not get an answer, so the five files of `fixtures/agent/` were written by hand. **We did:** a run served from a file whose `source` is `hand-built` has `model: "hand-built"` and `recorded: true`; once `python -m tta.agent.record` has replaced a sentence's files, its runs say `model: "recorded"`. **We got:** today both demo sentences show `hand-built` in the trace. **Example to show:** `POST /v1/agent/run` with scenario 2 and no key: `"model": "hand-built", "recorded": true`. **Ask:** "The trace says `hand-built` where the contract's comment only names `recorded`. Is that expected, or did we get something wrong?" **If no answer, we build:** as it is. A trace must not credit a model with an answer a person wrote. The pages (T12) should show the value as it comes.

## 3. For the team — "by Monday" said on a Monday
**Context:** the parser gives the model a calendar of the 14 days after the data clock's date and the rule "a weekday means the first such day after today". The parser itself only refuses a date before today. **We did:** wrote the rule; the live check got no answer, so no model has resolved a date yet. The hand-written recording of scenario 1 says Monday 16 Nov 2026 for the capture's clock (Saturday 14 Nov). **We got:** by the rule, the same words said on Monday 16 Nov mean Monday 23 Nov, not the same day. **Example to show:** the calendar and rule 2 in `tta.agent.prompts.parser_instruction(date(2026, 11, 16), keys)`. **Ask:** "On a Monday, 'by Monday' is read as next week's Monday. Is that expected, or did we get something wrong?" **If no answer, we build:** as it is: goods asked for on a Monday cannot arrive the same day (the cut-off is the day before).

## 4. For the team — the model cannot name an offer, a product or a quantity
**Context:** task T10: "product ids, prices, quantities and verdicts come only from tool results; the gateway refuses anything else". **We did:** the model sees four functions. `get_authority`, `create_offer` and `get_order` take no arguments; `place_order` takes `option_id` only. The runner binds the rest: the offer is built for the request the parser read, an order names an option of the latest offer of the run, and one run places one order. An option the gateway never issued is refused by the gateway (`not-found`). **We got:** a scripted model that tries `create_offer(quantity=10000)`, `place_order(option_id, quantity=10000)`, another offer's id and `opt_99` gets four failed steps, and the one order placed is option 1 of the offer, 200 units. **Example to show:** `tests/agent/test_guardrails.py::test_a_model_that_obeys_the_injected_instruction_can_still_only_order_an_option_of_the_offer`. **Ask:** "The agent's functions are narrower than the REST and MCP ones (no `offer_id` argument). Is that expected, or did we get something wrong?" **If no answer, we build:** as it is. It is the stricter reading, and it is what lets a recorded run be replayed: offer ids are random, option ids are not.
