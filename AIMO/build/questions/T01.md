# T01 — questions

## Q1 — for Valio: is an explicit User-Agent a requirement for agents calling the API?

**Context:** the API sits behind Cloudflare. The brief asks how a wholesaler can be "safely and openly readable by autonomous agents"; many agents call through a generic HTTP library with its default user agent.

**We did:** sent the same key with two user agents. `AIMO/FINDINGS.md` §1 records the first pair (14 Nov, 02:40, `GET /api/ping`); this task's client sent one `/api/availability` and one `/api/price` call at 03:13 with `User-Agent: tta-gateway/0.1`.

**We got:** 02:40 — HTTP 403 with Python's default user agent, HTTP 200 a minute later with `tta-preflight/1.0` (from FINDINGS; not repeated by this task, which had two calls to spend). 03:13 — HTTP 200 on both calls with the explicit user agent.

**Example to show:** the same `GET /api/ping` with `X-API-Key` set, once with the HTTP library's default `User-Agent` and once with `User-Agent: tta-gateway/0.1`. FINDINGS does not record the exact default string that was refused; note it when showing this.

**Ask:** "A call with a library's default User-Agent got 403 from Cloudflare while the same key with a named User-Agent got 200 — is that expected, or did we get something wrong? If it is expected, is a named User-Agent the rule an external agent should follow, and is there a list of what is refused?"

**If no answer, we build:** the client always sends `User-Agent: tta-gateway/0.1` and `Accept: application/json`; a 403 is reported once as `supplier-unavailable` with that hint and is never retried. The assumptions page says that agents must identify themselves.

## Q2 — for the team: which date does the gateway send as `requestedDate`?

**Context:** both endpoints require `requestedDate` ("the desired delivery date"). The `ValioGateway` port is `price(product_ids)` and `availability(product_ids)`: it carries no date. The mock ignores the date (FINDINGS §1: 24 products × 4 dates, identical product fields).

**We did:** the client sends the clock's current date. The two live calls at 03:13 sent `2026-11-14`.

**We got:** `pricingDate` echoed as `2026-11-14T00:00:00+02:00`; all 14 product lines equal to tonight's capture, which was taken with `2026-11-16`.

**Example to show:** `469363`: 384 `ST`, €2.48, cut-off Sunday 15 Nov 17:00, `availableDate` 2026-11-16 — the same answer for both dates.

**Ask:** "Should the buyer's `needed_by` be passed down to the Valio call, so that a real API that honours the date gets the right one? That needs a `requested_date` argument on the two port methods."

**If no answer, we build:** the clock's current date, as now. The needed-by date is compared with `availableDate` in our own code (SPEC §4), so the demo does not depend on it.
