**Context:** SPEC §2 names eight MCP tools and one of them, `get_offer`, is the only offer tool. REST has two offer functions: `POST /v1/offers` makes an offer (operation id `create_offer`) and `GET /v1/offers/{id}` reads a stored one (operation id `get_offer`). The task's test says "`get_offer` in replay returns the same offer as the REST route for scenario 2", and SPEC §11 describes the agent's loop as "read authority → get offer → place the order". **We did:** the MCP tool `get_offer` takes the typed request and calls `service.create_offer`: every call makes a new offer. No MCP tool reads a stored offer by its id. **We got:** the whole flow runs over MCP. But when `place_order` answers `offer-stale` or `offer-expired`, the problem carries `fresh_offer_id` (a new offer the gateway already made for the same request), and an MCP agent has no tool to read it: it has to call `get_offer` again, which makes one more offer and writes its events to the trail. And the name `get_offer` means two different functions on the two transports. **Example to show:** `tests/mcp/test_errors.py`, `test_a_changed_price_is_offer_stale_and_names_the_fresh_offer` (scenario 2 with every price raised by €0.10 between the offer and the order). **Ask:** "Over MCP the agent cannot read the fresh offer that `offer-stale` names, only ask for another one — is that expected, or did we get the tool wrong?" **If no answer, we build:** nothing more; the description of `place_order` tells the agent to ask for a new offer with `get_offer`. Changing it is about ten lines and one test: an optional `offer_id` argument on `get_offer` that calls `service.get_offer` instead.

**Context:** `create_app` mounts the MCP surface at `/mcp` (`src/tta/api/app.py`) and the pages at `/` for every path nothing else took. A Starlette mount at `/mcp` matches `/mcp/` and what is under it, not `/mcp` itself. **We did:** the MCP endpoint is the root of the mounted application, as the task says, so its address is `/mcp/`. **We got:** `POST /mcp/` is the MCP endpoint. `POST /mcp` without the last slash is answered with a 307 redirect to `/mcp/` when the pages are not mounted, and **by the pages application when they are mounted** (`TTA_ENV` `dev` or `demo`, so also on the demo link): an MCP host given `https://<host>/mcp` gets a page, not the protocol. Behind a proxy that ends TLS the redirect also names `http://` unless uvicorn trusts the proxy's headers. **Example to show:** with a stand-in `tta.ui.routes` mounted: `POST /mcp` → `200 "pages at /mcp"`; `POST /mcp/` → `200 {"jsonrpc":"2.0","id":1,"result":{"tools":[…]}}`. Without the pages: `POST /mcp` → `307`, `location: http://127.0.0.1:18711/mcp/`. **Ask:** "Most people will type `/mcp` without the slash and on the demo link that reaches the pages — is that expected, or should `app.py` send the exact path `/mcp` to the MCP surface as well (as it now does for `/v1`)?" **If no answer, we build:** nothing in T11 (the file is not ours). Every document and the demo script must give the address with the slash: `https://<host>/mcp/`.
