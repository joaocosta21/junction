# T09 — questions

All four are for the team, not for Valio.

**Context:** SPEC §9 lists "request received" as the first step of a trail, and the trail of an order is found through its offer id. `request.received` is written by `parse_request` and `run_agent` with the pasted text, before any offer exists (task note). **We did:** as the note says; `create_offer` writes `request.parsed`, `lookup.performed`, `offer.created` and one `policy.evaluated` per option, each with the offer id. **We got:** the trail of an order starts at "The request was read as: 1,000 litres of product type milk with claim FREE_FROM_LACTOSE, needed by Monday 16 November 2026." The pasted sentence ("The agent sent a request for profile hotel-kitchen: "1,000 litres of lactose-free milk by Monday".") is only in the buyer's whole trail (`GET /v1/audit` with no id). The buyer's words are still in the order's trail as a fact (`facts.request.lines[].text`), not as a sentence. **Example to show:** `GET /v1/audit?order_id=…` against `GET /v1/audit` after `POST /v1/agent/run`. **Ask:** "An order's trail has no 'request received' sentence — is that expected, or did we get something wrong?" **If no answer, we build:** as described. One line would change it: `create_offer` also writes `request.received` with the offer id and the lines' own `text`; then `parse_request` and `run_agent` would write it twice unless they stop. A request id on `AuditContext` is the clean way.

**Context:** SPEC §2: "Approval routes reject agent tokens". The order book (T08) lets an agent read its buyer's approvals and refuses it only on a decision. **We did:** the gateway service refuses an agent on `GET /v1/approvals` (403 `not-authorised`, no audit event) and on the decision route (403, with the `authorisation.refused` event of rule F-06). An approver may read its buyer's authority, catalog, offer, orders and audit trail, because choosing another option needs the offer. **We got:** the agent learns the state of an approval from its order only (`status`, `approval_id`, `status_sentence`, `decision.required_roles`). **Example to show:** `tests/api/test_identity.py`, `test_an_agent_token_on_the_approval_routes_is_refused_and_the_attempt_is_recorded`. **Ask:** "The agent cannot list approvals at all — is that expected, or did we get something wrong (should it read, and only be refused on deciding)?" **If no answer, we build:** as described.

**Context:** the per-token rate limit covers every function that reaches the supplier or writes to the audit trail (offers, substitutes, orders, approval decisions, parse, agent run). The demonstration tokens are public, so every visitor of the demo shares one token per identity. **We did:** 60 calls per minute for a token from the environment, 240 per minute for a demonstration token; one run of the buyer agent counts three (run, offer, order). In memory, per process. **We got:** about 80 agent runs per minute per demo identity before a visitor sees `rate-limited` (429 with `Retry-After`). **Example to show:** `tests/api/test_limits.py`. **Ask:** "During peer review several people use the same demo identity at once; 80 runs a minute per identity before a 429 — is that the right trade, or should the demo be wider or narrower?" **If no answer, we build:** as described (`DEMO_RATE_LIMIT_CALLS` in `src/tta/api/limits.py`, or `build_parts(settings, rate_limit=RateLimit(...))`).

**Context:** the pages (T12) act as a demonstration identity chosen on the page, with no token. **We did:** `tta.ui.routes` is mounted at `/` only when `TTA_ENV` is `dev` or `demo`; `SurfaceContext.demo_identities` is empty anywhere else. The MCP surface is mounted in every environment, since it takes the same bearer token as REST. **We got:** with `TTA_ENV=prod` the gateway has no page at `/` (404) and no surface that acts without a token. **Example to show:** `tests/api/test_hooks.py`, `test_outside_dev_and_demo_the_pages_are_not_mounted_and_no_demo_identity_is_handed_out`. **Ask:** "No pages outside dev and demo — is that expected, or did we get something wrong (pages with a login are a next step)?" **If no answer, we build:** as described.
