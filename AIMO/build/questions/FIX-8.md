**Context:** the demo tokens are public, so the limit per caller is now per visitor: the identity plus a client key. The task defines the key as the direct peer's address, or the first address of `X-Forwarded-For` when the direct peer is a private or loopback address. Whether that tells visitors apart depends on what the host puts in front of the app. **We did:** built it as the task says (`client_key_of` in `src/tta/api/limits.py`). Python's `is_private` is true for 10/8, 172.16/12, 192.168/16, loopback, link-local and the documentation ranges, and false for the shared range 100.64.0.0/10. **We got:** checked against uvicorn on this machine and in tests only; nothing was run on Modal. If Modal hands the app the visitor's own address as the peer, each visitor has its own window. If it hands the app a proxy address that is private, the header decides, and a visitor who forges the header gets a new window per forged address (the three ceilings for all callers still hold). If it hands the app a proxy address that is not private (for example in 100.64.0.0/10), every visitor has the same key and they share one window of 60 a minute per demo identity, which is the lock-out this fix was meant to remove. **Example to show:** on the deployed app, two phones on different networks each send three offers with `demo-agent-allergy-ward` while the limit is set to 2: both must get two answers of 201 and one of 429. `tests/api/test_visitors.py` shows the three cases with a stand-in peer. **Ask:** "On Modal, is the address the app sees as its peer the visitor's, a private proxy address, or something else — is the per-visitor window working there, or did we get the rule wrong?" **If no answer, we build:** as described. If the peer turns out to be a proxy address that is not private, the change is one line in `client_key_of` (believe the header from any peer that is not a global address).
