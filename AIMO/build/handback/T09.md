## Assumptions
- Who may call what: an agent everything of its own buyer except the approval routes; an approver the reads of its own buyer (authority, catalog, offer, orders, audit) and the approval routes; the supplier the audit route only. An agent on `GET /v1/approvals` is 403 (question 2).
- The limits live in the service, not in the routes, so MCP tools, pages and the buyer agent get them too.
- Rate limit: 60 calls per 60 seconds per identity for tokens from the environment, 240 for the shared demo tokens (question 3). Counted per identity id (one token is one identity). In memory, one process. A call the service refuses for its kind of identity writes nothing and is not counted; an agent on the decision route is counted, because that refusal writes an event.
- Body over 64 KB: status 413 with type `invalid-request`. A request that fills every field of the contract to its maximum is larger than 64 KB and is refused.
- A request names at most 1,000 product ids over all its lines (the contract allows 1,000 per line and 20 lines).
- Lists: at most 100, the newest (orders newest first; approvals and audit events in time order). A search is cut to 100 products; `total` and `note` say how many match. No paging.
- No problem has an `instance`: the path holds text the caller sent. 404 and 405 of the router and the 500 use type `about:blank`.
- A validation problem lists `errors[]` as `{field, problem}`; an unknown field is named by where it sits, never by its key; Pydantic's message is replaced by its error code when it repeats the input.
- A Pydantic `ValidationError` raised below a route is `invalid-request` (task note), also when the fault is ours.
- `POST /v1/offers` and `POST /v1/orders` answer 201, the retry with the same key too.
- `?status=` on approvals takes any case (`pending`, `PENDING`).
- `request.parsed` has the agent as actor; lookup, offer and policy events the system.
- When no fresh offer can be built after `offer-stale` / `offer-expired`, the 409 is sent without `fresh_offer_id` and the reason is logged. Only `place_order` gets a fresh offer, not an approver's decision.
- Fall-back: after a live failure the capture answers for 30 seconds before the live API is tried again, so one lookup stays on one source and requests do not wait through the client's retries. Below 10 calls left, the capture answers. Before any answer `source` is where the budget lets the first one come from.
- If the live client cannot be built (address not https), live mode runs on the capture and logs it. If the capture cannot be read, the app does not start, in either mode.
- Outside dev and demo: `TTA_TOKENS` is a JSON object token → identity (the fields of `Identity`); missing, not JSON, empty, an empty token, an invalid identity or an unknown profile stops the start. The error names the entry's position, never a token.
- Pages are mounted only in dev and demo (question 4). A missing optional module is skipped; one that exists and breaks, or lacks its hook, stops the start.
- The pages get every path nothing else takes, except paths under `/v1/`: a path or method the API does not have is answered by the API as a problem document (404, 405), not by a page.
- `/healthz` is public: environment, mode, source, audit head (count and last hash), `settings.describe()`, which hooks are in.
- OpenAPI examples use identities made from the profiles (`agent:<profile id>`, the first approver listed for the role), not the demo tokens, so they are the same in every environment. The `run_agent` example trace is put together from the gateway's answers of scenario 2; no model is called for an example.

## Contract changes needed
- `GatewayService`: add `list_orders(identity)`; the service has it, the port does not.
- `AuditContext` / `AuditData`: a request id, so `request.received` belongs to the trail of the order it led to (question 1; T06 raised it).
- `AuditView`: a total or a "cut" flag; a view cut to 100 events says so only through `chain.checked`.
- `Store` / `AuditSink`: a cheap count and head; `/healthz` calls `head()`, which reads every event.
- `PlaceOrderRequest.offer_id`, `.option_id` and `DecisionRequest.option_id`: unbounded strings. The routes bound path and query ids (64 characters of `[A-Za-z0-9_-]`); the body fields need it in the contract.
- `OfferLine.tax_rate` and `RelianceStatement.available_amount` leave as JSON strings (`"13.5"`, `"478.0"`); SPEC §2 says numbers.
- `tta.contracts.errors`: no type for a body that is too large or for an internal fault (see assumptions).
- `Settings`: no field for the rate limit or the body limit; they are constants in `tta/api/limits.py`.
- `UnknownProduct` raised by `tta.offers` carries the `product_id` the caller sent as an extension member (20 alphanumeric characters at most). Owner: offers.
