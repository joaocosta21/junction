## Assumptions
- `decide` follows the port (`decide(approval_id, identity, DecisionRequest)`), not the keyword form in the task text.
- Stale or expired is read from F-04's facts (`option.expired`, `revalidation.expired`): either true → `offer-expired`, otherwise `offer-stale`. When F-04 fires with another blocking rule, F-04 decides the error.
- Extension members: `offer-stale` has `changes` (the `RevalidationChange` objects), `offer-expired` has `valid_until`, `policy-blocked` has `rule_ids` and `reasons`; all have `offer_id`, `option_id`, and `order_id` when raised from `decide`.
- The revalidator raising `SupplierUnavailable`: one `order.not_placed` event with no decision, the error passes through, nothing is ordered or decided.
- Idempotency keys are scoped to the agent id. A key is bound only when an order is created: after `offer-stale`, `offer-expired` or `policy-blocked` the same key is checked again (the store can bind a key to an order id only, not to an error).
- The option first asked for is kept in `Order.extra["requested_option_id"]`, so a retry still returns the order after an approver chose another option.
- A blank key is `invalid-request`. Only an agent places an order; anyone else is `not-authorised` with no audit event. An agent ordering from another buyer's offer is `not-authorised`.
- An id nobody issued is `not-found`; the id a caller sent is never echoed in an error detail or in the audit trail.
- Reads: another buyer's order or approval is `not-authorised` (403), not `not-found`; the supplier is refused before any lookup. A refused read writes no audit event. An agent may read (not decide) its buyer's approvals. `list_approvals` returns every approval of the buyer, not only those waiting for the caller's role.
- `decide` checks in this order: approver at all (else refused; an agent is F-06) → approval exists → same buyer and listed in the profile → order still waiting → holds a role still missing.
- A rejection also needs a role still missing; a rejection with `option_id` is `invalid-request`. An approver whose role is already given cannot decide again (`not-authorised`).
- An approval already closed is `invalid-request` (no conflict type exists).
- Every approval, not only the last, re-checks and re-evaluates at order time. The roles, reasons, decision, option and reliance statements of the order become those of that evaluation, so a role the policy asks for only now (the day's spend grew) is added, and one it no longer asks for is dropped.
- The day's spend at approval leaves out the order being decided.
- Choosing another option starts the approval again: earlier approvals were for another option and no longer count (question 2). Naming the option already proposed is not a change.
- `ApprovalDecision.roles` holds the roles that count for this buyer, not every role in the token.
- A failed re-check at approval changes nothing: the order keeps waiting (question 1).
- Expiry: strictly after the ordered option's `valid_until` (at that instant it can still be decided, as in the policy); no `valid_until`, no expiry. Applied on `get_order`, `get_approval`, `list_approvals`, `decide` and an idempotent retry. Deciding too late expires the order and answers `offer-expired`.
- The day's spend counts by `created_at` on the clock's date, in the clock's offset. A pending order past its time is not counted, even before it is read. The function writes nothing.
- Every time on an order or approval is the data clock's. In replay all orders carry the capture's time and all are "today".
- `Order.option.decision` is the order-time decision, equal to `Order.decision`; the stored offer keeps its own.
- Reliance statements take their values from the option's lines (the fresh check confirmed them unchanged); `time_now` and `source` are the check's.
- An order completed by a human is `HUMAN_APPROVAL` even when the policy asks for nobody any more at that moment.
- Audit actors: the agent; a human with `role` = the token's roles joined by ", "; the system actor for `order.confirmed`, `order.rejected`, `order.expired`.
- A refused decision is filed with the approval it was aimed at (question 3). For an approval nobody issued, only the caller's own profile is recorded.
- One in-process lock serialises `place_order`, `decide` and reads that expire; it is held during the fresh check, so a slow supplier call delays other orders.
- State is saved first, then the audit event is written.

## Contract changes needed
- `tta.contracts.errors` — no conflict type (409): deciding a closed approval is `invalid-request` (422).
- `Order` — a field `requested_option_id` instead of `extra["requested_option_id"]`.
- `ActorKind` — no kind for the supplier reader: a refused supplier is a human with role `supplier`, and the supplier view shows it as "A human at the buyer".
- `Store` — no version check and no unit of work over order, approval and audit event; `remember_idempotency_key` cannot hold an error outcome.
- `AuditEventType` — nothing for a refused order placement or a refused read.
- `tta.orders.wording` imports `ended`, `joined`, `moment`, `money`, `person`, `roles_text` from `tta.audit.phrases` (a cross-package import of pure functions, so status sentences read like the trail). A shared module would remove it.
- `OrderService` has no `list_orders`; T12 needs one only if a page lists orders.
