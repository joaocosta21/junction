## Assumptions
- **Callers must pass `PolicyContext.day_committed_net_eur`, also when the offer is built.** `None` is a missing fact: every option then reads `APPROVAL` by F-03 (finance). T07 needs the day's spend (`OrderService.day_committed_net_eur`) to put a true verdict on an option.
- **At order time (`at_order_time=True`) callers must pass `revalidation`, and the option must carry `valid_until`.** Either one missing is F-03 (`APPROVAL`), never `AUTO`. T08 fixtures built by hand need `valid_until`.
- F-04 is evaluated only when `context.at_order_time` is true. It fires when `option.valid_until` is earlier than `context.now`, or when the revalidation is not ok. A revalidation with `ok=True` but `expired=True` or any change listed is read as not ok. `FiredRule.facts` of F-04 carries `revalidation.expired` and `revalidation.changes`, for T08 to choose between `offer-expired` and `offer-stale`.
- F-01 fires for every availability state other than `CONFIRMED`, and for a `CONFIRMED` line whose `quantity` claim is not `CONFIRMED`.
- F-02 and P-04 read the outcomes of the line's `AllergenCheck` (its own and each finding's): `REJECT` → F-02, `TO_HUMAN` → P-04. The relations are not re-read: the table of SPEC §6 stays in `tta.allergens` (declared oats under a gluten exclusion go to the dietitian, not to a block).
- For a profile that excludes allergens, each line needs an `AllergenCheck` with one finding per excluded code (`excluded_code` = the buyer's code) and, for a `STRICT` profile, `strictness=STRICT`. Otherwise F-03 (dietitian). Checked against `src/tta/allergens/exclusion.py` as it stood at hand-back: it does both.
- `allergen_check=None` on a line of a profile without exclusions means nothing was excluded; it is not a missing fact.
- F-05 follows `substitute.allergen_check.passes`.
- `OfferLine.variable_weight=None` is F-03. Catalog figure: 3,068 of 17,546 products do not state `variableUnit`, so any option holding one of them goes to a human.
- F-03 lists one entry per missing fact and line, naming the rules that needed it. Its role comes from the fact: finance for the day's spend, dietitian for the allergen check, otherwise purchasing manager.
- P-01 and P-02 fire strictly above the limit; P-03 strictly below the minimum. P-02 compares `day_committed_net_eur + totals.net` with `max_daily_net_eur`.
- Roles SPEC §7 does not name: P-00, P-05 and P-06 go to the purchasing manager (P-05 and P-06 as in Gabriela's file).
- `SAME_CATEGORY` includes substitutes listed by the supplier; "same category" is `category_distance` 0 (question 1).
- P-06 with `AUTO_WITH_CEILING` lets the agent order alone only when `totals.is_ceiling` is true; P-07 with `NOTE` only when `totals.excludes_deposits` is true.
- `allergy-ward`: `variable_weight` and `deposits` are `APPROVAL`; SPEC §7 sets neither (question 2).
- `approver_roles` hold only the three identities of `tests/conftest.py`. No one holds dietitian for `hotel-kitchen`, or purchasing manager or finance for `allergy-ward` (question 3).
- The engine does not read `require_confirmed` or the `price`, `delivery_date` and `origin` claims: SPEC §7 has no rule for them (question 4).
- A `BLOCK` decision has no `required_roles`. An `APPROVAL` decision requires the roles of every rule that asks for a human.
- `PolicyDecision.sentence` names only the rules that decide the verdict; `fired` lists all of them. `FiredRule.sentence` is a full sentence without the rule id.
- Numbers in `FiredRule.facts` are JSON numbers rounded as the contracts do (money 2 places, ratio 4). In sentences totals print with two decimals (€428.00) and limits as set (€750).
- Policy hash: `sha256:` + hex, Gabriela's format. `750` and `750.00` in a profile hash alike; comments and key order do not change it.
- A profile file's name must equal its `profile_id`. Any key outside the `BuyerProfile` contract is rejected, so a profile has no way to address a rule at all.
- F-06 is in `rules.yaml` as an access rule: covered by the hash and by `Authority.summary`, not evaluated by the engine. T08 and T09 enforce it.
- Gabriela's P-11 (not deliverable), P-13 and P-14 (pack size estimated or unknown) and P-15 (lot step) are not carried over: SPEC §7 does not list them and the offer excludes those products.
- `get_profile` raises `NotAuthorised` without echoing the id. A broken rules or profile file raises `PolicyLoadError` at start-up.
- The rules file and the profiles are read from the package folder; `from_files(rules_path, profiles_dir)` takes other paths. `Settings` has no policy path.
