## Assumptions
- **`LiveClock` does not stand still between answers.** The task says "the `timeNow` of the last response, else UTC now". Built: the last `timeNow` plus the time passed since it was seen (this machine's wall clock, which keeps counting through sleep). A clock frozen at the last answer would never expire a pending approval on read (T08) until the next Valio call. One line to change in `clock.py` if you disagree.
- Before the first availability answer the clock is UTC now; after it, the time carries Helsinki's offset. Around midnight "today" can differ between the two.
- Only a live availability answer moves the clock: `/api/price` states no server time, and a cached answer is not a new observation.
- `requestedDate` sent is the clock's current date. The port carries no date and the mock ignores it (FINDINGS §1). Question T01-Q2.
- `PriceResponse.retrieved_at`: live, the clock's time when the answer arrived; replay, the capture's `time_now`.
- Availability over several chunks reports the latest `timeNow` of its chunks; replay reports the manifest's `time_now` on every answer.
- The cache key is the endpoint plus the sorted distinct ids of the whole call. A subset or superset is a new call. A hit returns the lines in the order of the first call (use `by_id()`), costs no budget and is not recorded again.
- The budget counts every HTTP attempt, retries included, before it is sent. The limit is `TTA_VALIO_CALL_BUDGET`; only the count is in the file. A budget file that cannot be read stops every call rather than starting again from zero. There is no lock between processes.
- Retries: a time-out or a 5xx, after 1 s and then 2 s, three attempts in all. A 4xx (429 included), a connection failure and an unreadable body are reported at once.
- The one-second gap runs from the end of a call to the start of the next. One client makes one call at a time (a lock), so parallel requests queue.
- Every failure is `SupplierUnavailable`: no key, budget spent, HTTP error, unreadable answer, unusable capture. An httpx error is never chained to it, because it holds the request and the request holds the key.
- Parsing is strict. A body that breaks the published shape (a required field missing, more than one schedule line, a time without an offset) refuses the whole answer; so does an answer that leaves out a requested id. Products nobody asked for are dropped. An error names the field, never the text found in it.
- An answer whose text contains the API key is refused and not recorded.
- Recorded: every 200 answer that parsed, byte for byte. Not recorded: error bodies. For a price answer the recorded `time_now` is the clock's time at retrieval.
- If an answer cannot be recorded, or the budget cannot be saved, the call fails. Live mode needs a writable `TTA_DATA_DIR` (relevant for T14).
- Replay: an id outside the capture is answered as the live API answers an unknown id — price `error: true`, availability with no schedule line. Confirmed live tonight with `459999`.
- An empty id list returns an empty answer without a call (the API would answer 422).
- `priceWithTax` is not read: the contract has no field for it and `catalog_price.value_with_tax` carries the same figure.
- User agent `tta-gateway/0.1`; time-outs 5 s to connect, 30 s to read. Redirects are not followed.
