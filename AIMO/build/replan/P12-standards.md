### 2.3 Departures the documents do not list
- **`Origin`, still open.** A request to `/mcp/` with `Origin: https://evil.example` gets 200 and the 8 tools (`check2.py`). The current revision adds: "If the `Origin` header is present and invalid, servers **MUST** respond with HTTP 403 Forbidden" (same URL as E). The document admits the missing check (`docs/STANDARDS.md:80`); it is the only MUST we break. The SDK already has the setting: `TransportSecuritySettings` has `allowed_hosts` and `allowed_origins` (`check4.py`); we switch it off at `src/tta/api/mcp_surface.py:316`.
- **`server/discover` advertises more than we have.** At 2026-07-28 it lists `prompts`, `resources` with `subscribe: true`, and `listChanged: true`; the 2025-11-25 `initialize` says `false`. The server has tools only and no stream (`check2.py`). This is the SDK's default; not checked further.
- **Idempotency-Key, two departures.** A missing header → 422 (`check1.py`); the draft says the server "SHOULD reply with an HTTP `400` status code". The draft makes the value a Structured Field String ("Its value MUST be a String"), which is written in double quotes; our pattern `^[A-Za-z0-9._:-]+$` refuses the quoted form with 422 (`check4.py`).
- **Bearer challenge differs by surface.** REST answers an unknown token with a bare `WWW-Authenticate: Bearer`; MCP answers `Bearer error="invalid_token", …` even with no token (`check1.py`, `check2.py`). `docs/STANDARDS.md:85` quotes the `invalid_token` rule and `:87` then describes the bare header without calling it a departure.
- **201 without `Location`.** `POST /v1/offers` and `POST /v1/orders` answer 201 with no `Location` header (`check1.py`). An agent must read the id from the body.
- **No discovery document.** `/.well-known/api-catalog`, `/.well-known/mcp.json`, `/.well-known/mcp/server-card.json`, `/.well-known/agent-card.json`, `/.well-known/ucp`, `/.well-known/oauth-protected-resource`, `/llms.txt`, `/robots.txt`: all 404 (`check1.py`). `/openapi.json` has no `servers` and no `externalDocs`.

### 2.5 What we do and do not claim (free points)
- **GTIN.** `GET /v1/products/{id}` and search return `sales_unit_gtin`, `synkka_gtin` and `units[].gtin`. All 7 demo products have one, for example `469363` → `6413300011517`, `464013` → `5411188115496` (`check3.py`). Whole catalog: `salesUnitGtin` is present on 17,387 of 17,546 products (`AIMO/docs/FIELD-DICTIONARY.md:187`). `docs/STANDARDS.md` never says "GTIN". Offer and order lines do not carry it (`OfferLine` has no such property, `check2.py`).
- **ISO 3166-1.** `country_of_origin` is alpha-2 (`BE`), `countries_of_origin` numeric (`056`) (`check3.py`). Caveat: `zy`, `xs`, `zz` on 195 products are not ISO codes (`AIMO/docs/PRODUCT-DATA.md:404`).
- **GS1 Synkka.** The product file's `synkkaData` block is the "Manufacturer-supplied GS1 Synkka block" (`AIMO/docs/PRODUCT-DATA.md:26`). Synkka is GS1 Finland's GDSN data pool (search result, GS1 registry statistics: https://www.gs1.org/sites/default/files/docs/gdsn/stats/gdsn_dp_activity.pdf). So the allergen codes, nutritional claims and labels we read are already standard data that Valio's suppliers publish. Assumption to verify: that the claim and label ids are GDSN code lists.
- **Units are not standard codes.** Lines use Valio's `ST`, `KI`, `PAL` ("technical codes", `AIMO/docs/FIELD-DICTIONARY.md:200`); requests use our `L`, `KG`, `UNIT`. Peppol requires a unit code on every quantity from "Recommendation 20, including Recommendation 21 codes - prefixed with X (UN/ECE)" (https://docs.peppol.eu/poacc/upgrade-3/). We claim no unit standard, so nothing is false; it is the main gap of any order mapping.

## 3. What Valio's answers change
- **V8 (no automatic order for now).** The MCP instructions and `place_order` text say "`AUTO`: the order is `ORDERED`, placed by you" (`src/tta/api/mcp_surface.py:77-80`, `:240-243`), and the OpenAPI description says the same. If the team switches automatic ordering off, these texts and the STANDARDS page change with it. It also makes the standards story simpler: a human's confirmation of a final cart is what AP2 calls a closed checkout mandate, and what a Peppol order commits.
- **V5 (noisy data; flag when unsure).** This is the brief's "trust protocol". Our per-claim status is the right shape. The standards-based next step for it is signed statements (already next step 7, W3C Verifiable Credentials) and GS1 identifiers on every line (W4).
- **V9 Q2 ("take the values as they are").** Two lines of STANDARDS are out of date (§2.4, `:15`, `:103`).
- **V9 B13 (Valio sees "all the steps and decisions").** If the supplier view widens, an audit export (W6) gets simpler: fewer fields to hide.
- **V1 and V2 (customer data is generated; per-user patterns).** "Real customer limits" stays a next step; the integration point is Valio's customer master and contract prices, which the mock does not have.
- **V7 (category numbers: "sap code semi random").** A hint, not a fact, that the order entry behind the mock is SAP. Do not map our `category` to a public classification.

### x402 and Nevermined
- **x402.** "x402 is an open, neutral standard for internet-native payments." A request without payment gets HTTP 402, "prompting the client to pay and retry". "Stablecoin payments are the primary use case." "x402 is free for the customer and the merchant—just pay nominal payment network fees." (https://www.x402.org/). The repository moved to the x402 Foundation; the page links the Linux Foundation's announcement of it. The server sends its terms in a `PAYMENT-REQUIRED` header, the client pays with `PAYMENT-SIGNATURE`, the answer carries `PAYMENT-RESPONSE`; a "facilitator" verifies and settles; schemes are `exact`, `upto` and `batch-settlement`; "x402 may extend support to fiat based networks, but will never deprioritize onchain payments in favor of fiat payments" (https://github.com/coinbase/x402). Status: an open specification under a foundation, not a standards-body document as far as these two pages say.
- **Nevermined.** A company's product, not a standard: "Nevermined - Payments Infrastructure for AI Agents". "Your agents spend inside a mandate you set"; a spend mandate is "The limit you set before an agent can pay: an amount, an expiry and a number of purchases." It names "Protocols x402 · MPP" and "settles the merchant on the rail they take: cards, Visa agentic tokens or crypto" (https://nevermined.ai/). I did not read what MPP is.
- **Our position, one paragraph for STANDARDS.** "No payment happens in this flow, by design. Valio Aimo's customers buy on account at fixed prices and are invoiced after delivery; for goods sold by weight the amount is only known then (Valio, 14 Nov: invoiced for "what is actually delivered"). A protocol that settles at the moment of the request, such as x402, has nothing to settle here. Agent payments would matter in three places: a buyer with no account or credit line who prepays a first order; charging other platforms' agents for heavy price and availability lookups, where we answer 429 today and x402 would answer 402 with a price; and marketplaces of many small sellers. What we share with these products is the idea of a mandate: Nevermined's "amount, an expiry and a number of purchases" is our buyer profile's limit per order and per day, set by a human before the agent acts."

### The trust layer: the smallest real addition
- **W8, signed offers (2 h).** The gateway signs every offer and every order record with one Ed25519 key and publishes the public key. The answer gains an optional `proof` (key id, algorithm, a JSON Web Signature over the SHA-256 of the record's canonical JSON, the same form the audit chain uses, `src/tta/audit/chain.py:52`). The public key is served as a JSON Web Key set at an address named in the discovery document (W2). A 15-line script in the README checks a saved offer offline. With the same key, sign the audit head that `/healthz` already shows (plus 0.5 h): then the other party can check the chain's end, which is next step 4.
  - What it proves: "this gateway stated this price, this stock and these allergen statements at this time". It does not prove that Valio's data is true. In production Valio holds the key; here it is our demo key, and the page must say so.
  - `cryptography` and `pyjwt` are installed but only through other packages: they are not in `pyproject.toml`'s dependencies and would have to be added.
  - JSON Web Signature and JSON Web Key are RFC 7515 and RFC 7517 (numbers from memory, not re-read today).
- **A full Verifiable Credential: one paragraph, not before Sunday.** "Securing Verifiable Credentials using JOSE and COSE" is a W3C Recommendation (the page is dated 13 October 2026) and secures a credential as a signed JWT, media type `application/vc+jwt` (https://www.w3.org/TR/vc-jose-cose/). A real credential also needs a vocabulary for our claims, an issuer identifier with a key document, and a verifier on the buyer's side: 5 to 8 hours, and nothing more to show in a 2-minute video than W8. W8's signature is the same signature a credential would carry, so it is the first half of that road.
- **Not recommended: HTTP Message Signatures.** RFC 9421 (Standards Track, February 2024) signs "components of an HTTP message" and covers a body only through a `Content-Digest` field (https://www.rfc-editor.org/rfc/rfc9421.html). The proof would live on the HTTP answer, not on the stored offer, and would not travel through an MCP tool result.
- **DECISION 5 — build W8 or write the paragraph.** My recommendation: build W8 only after W1 and W2 are done and the demo path is green, by the computer-science member, in place of W6 and W7. It is the only item of this proposal that answers the brief's word "verifiable" with something a judge can check. If those 2 hours are not there, write the paragraph and the table above; they cost nothing and already show a trust layer.

## 7. Risks and what not to do
- Do not publish a well-known document for a protocol we do not implement (UCP profile, A2A agent card, MCP server card, OAuth resource metadata with no authorization server). A judge who probes it finds a false claim.
- Do not write "Peppol-compatible", "UCP-ready" or "AP2 mandates". We have mapping tables and no document that validates.
- W3: the app runs behind Modal's proxy. A wrong allow-list locks out a browser-based MCP host during the demo. Test on the deployed app; keep "no `Origin` passes".
- W4 changes a contract model. Keep the field optional; regenerate the examples (`src/tta/api/examples.py` builds them from real runs); run the whole suite.
- W6: say plainly that a reader of a redacted view cannot recompute the hashes.
- GTIN is not a key: the sales-unit and consumer-unit GTINs differ on 6,867 products and 27 are shared by 54 products (`AIMO/docs/PRODUCT-DATA.md:151`, `:842`). Carry the GTIN of the unit sold and keep `product_id` as the key.
- Do not change the problem-type base `https://tta.example/problems/` to the Modal address: a type URI is an identifier and should not depend on where the demo runs.
- W8: never commit the signing key; in `demo` generate one at start when none is set and say on the page that it is a demo key. Do not write "Valio signed this": the gateway signed it. Do not call the signature a Verifiable Credential.
- Do not add a payment step or a 402 answer to look current: the brief says agent payments are "not required", and our buyers are invoiced.
