# FEAT-1 — "Your kitchen": the buyer sets what its agent may decide alone

**Scores on:** the brief's third core requirement, "Permission & human-approval management: what the agent may decide on its own, and what must go to a human for sign-off" · 20% autonomy and controls ("quality of the guardrails design") · 30% demo. Requested by the human on Saturday ("what the agent may order alone should be like a profile setting").
**Read first:** `AIMO/build/AGENT-RULES.md`; `AIMO/WALKTHROUGH.md` sections 2, 3 (steps 1, 10, 11), 7 and 9; `src/tta/policy/` (profiles are YAML validated by `tta.policy.profiles`; fixed rules cannot be weakened; `RulePolicyEngine`); `src/tta/api/sandbox.py` (each browser's own order book, FIX-10/FIX-11); `src/tta/ui/` (pages, CSRF, CSP, escaping, the identity cookie).

## Build
- **A page `/kitchen`** (dev and demo only, like every page): a form to set up "My kitchen" — a display name; may the agent order alone at all; spend limit per order and per day (EUR); minimum share of the quantity covered; excluded allergens (GS1 codes with their names, from `tta.allergens`), with the strictness `STRICT` / `DECLARED_ONLY` required when any is chosen; substitutes without a human (none / listed by Valio / same category); variable weight and deposits (to a human or allowed with the note); confirmed data only. Start from a copy of `hotel-kitchen` or `allergy-ward` (two buttons). Show next to each setting the rule it drives (P-00 … P-07) in one plain sentence, and below the form the fixed rules F-01 … F-08 as "always, whatever you set".
- **Validated exactly as a profile file is:** the same `BuyerProfile` contract and the same loader checks (`tta.policy.profiles`), so a value out of range or an exclusion without a strictness is refused with the field named, and nothing can switch off a fixed rule. Bounds: limits 0 to 100,000 EUR; at most 10 excluded allergens.
- **It lives in the browser's own order book** (the sandbox): one custom profile per sandbox, profile id `my-kitchen`, with its own policy hash; an agent identity "My kitchen agent" bound to it, offered in the page's "who is asking" selector next to the two demo agents; approvals of `my-kitchen` are decided by the hotel's demo approvers (purchasing manager, finance, dietitian), listed in its `approver_roles`. It never reaches the shared REST book, the policy files on disk, or another visitor. "Start again" also clears it.
- **The authority page and the audit trail show it:** `GET /v1/authority` is not affected (REST has no custom profile); on the pages, the result of a run as "My kitchen agent" shows the profile's summary sentence (`describe_authority`) and the policy hash in force, and its audit trail names profile `my-kitchen`.
- **One demo moment in `docs/DEMO.md`** (append a short section): set the per-order limit to €3,000, run scenario 1 as "My kitchen agent" → option 1 (€2,580.64) is ordered by the agent alone; set it back to €750 → the same request goes to the purchasing manager. Say which criterion it scores on.

## Tests first
- The form round trip; every refusal names its field; a crafted POST that tries to set a fixed rule or an unknown setting is refused; CSRF required; text escaped.
- Scenario 1 as "My kitchen agent" with €3,000 per order → `AUTO` and ORDERED; with €750 → `APPROVAL` P-01; the hotel's own agent in the same browser is unaffected.
- Two browsers: one's profile never affects the other's offers.
