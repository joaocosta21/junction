# FIX-7 — Orders and store: one write or none, one order per offer, a daily limit that counts the right day

**Scores on:** 20% (controls: an order never exists without its audit event; a limit cannot be walked around) · 30% (the flow does not get stuck). From review round 2 (Python reviewer findings 1, 3, 4, 5, 7; silent-failure findings 4, 6, 7, 11, 12; security findings 3, 4, 6, 7).
**Owns:** `src/tta/orders/`, `src/tta/store/`, `tests/orders/`, `tests/store/` — except the function `is_past_order_by` in `src/tta/orders/records.py` and the tests of its boundary, which FIX-5 is changing to `<=` right now: read it, do not edit it. **Hand-backs to read:** `AIMO/build/handback/T08.md`, `T06.md`, `FIX-2.md`. **Read:** SPEC §8.
**Importers to re-run:** `tests/audit`, `tests/offers`, and `tests/api` if it exists by then.

## Findings to fix
1. **HIGH — the writes of one outcome are not atomic.** `service.py`: every status change saves the order, then the approval, then writes the audit event. Reproduced: with `save_approval` failing once, a retry with the same key returns a `PENDING_APPROVAL` order whose `approval_id` points at nothing, with no audit event, and nobody can ever decide it. The same gap exists in `_approve`, `_place_alone`, `_reject` and expiry. Fix with the new port method **`Store.atomic()`** (already in `tta/contracts/ports.py`): a context manager; everything saved or appended inside the block is committed together or not at all.
   - `SqliteStore.atomic()`: one transaction (`BEGIN IMMEDIATE` … `COMMIT`, `ROLLBACK` on any exception), re-entrant for the same thread; the store's methods, the audit append included, take part in it when one is open and behave as today when none is. The audit append's head check must still hold inside it.
   - Orders: each outcome (place alone, send to a human, approve, reject, expire, and the refused attempts that write an event) does its saves, its idempotency binding and its `audit.record` inside one `atomic()` block. If the audit write fails, nothing is saved and the caller gets the error.
   - Tests: fault injection on each write of each outcome (make the second or third write raise): afterwards the store holds nothing of that outcome and a retry with the same key succeeds cleanly.
2. **MEDIUM — the same offer can be ordered twice under two keys.** Reproduced: two keys, one offer and option, two `ORDERED` orders. An offer answers one request: while an order of that offer is `PENDING_APPROVAL` or `ORDERED`, a second `place_order` on the same offer (any option, any key other than the first) is `InvalidRequest`, saying that the offer already has an order and giving its id (it is the caller's own buyer's order). After `REJECTED` or `EXPIRED` the offer can be ordered again.
3. **MEDIUM — roles are checked against the old option.** `decide` checks the approver's roles against `approval.roles_missing` before the order-time policy runs; after another option is chosen, or the day's spend changed, the policy may ask for other roles, so the right person is refused and the approval stalls. Run the order-time check first, then decide whether this approver holds a role the new decision still needs.
4. **MEDIUM — the day's spend counts the wrong day.** `spend.py` dates every order by `created_at`. An order created on day 1 and approved on day 2 is spend of day 2. Count an `ORDERED` order on the date it became `ORDERED` and a `PENDING_APPROVAL` order on the date it was created; keep both in the data clock's offset.
5. **MEDIUM — only one kind of failure is recorded.** `checking.py` writes `order.not_placed` when the re-check raises `SupplierUnavailable`. Any other exception from the re-check or the policy leaves an attempted order with no event. Record `order.not_placed` for any failure of the check (the event's facts carry the error type, never its text), then re-raise.
6. **MEDIUM — what the order "relied on" is mislabelled.** `records.py` (`reliance_statements`) stores the offer's figures stamped with the re-check's time. `RelianceStatement` now has `rechecked_at`: set `time_now` to the offer's data time (when Valio stated the figures) and `rechecked_at` to the time of the re-check that found them still sufficient.
7. **MEDIUM — an approval with no "order by" time never expires.** When the option has no `valid_until`, the approval gets `valid_until` = its creation time plus 24 hours (a named constant), and the status sentence says the order waits until then.
8. **LOW — expiry does not converge in the same call.** When `decide` finds the order past its time, it marks it `EXPIRED` with the event in that call (inside the atomic block), then answers `offer-expired`.
9. **LOW — another buyer's id is distinguishable from an unknown one.** `get_order`, `get_approval`, `decide` and the offer lookup answer `not-authorised` for another buyer's id and `not-found` for an unknown one. Answer `not-found` for both. A refused attempt on another buyer's approval is recorded in the caller's own trail (its profile), not in the trail of the buyer it aimed at.
10. **LOW — the idempotency key is unbounded.** Accept 1 to 100 characters of `[A-Za-z0-9._:-]`; anything else is `InvalidRequest`.

## Known and left as it is (say so in the hand-back, do not build)
The one lock in the process is held across the supplier call, and it protects one process only. With `atomic()` the store keeps the data consistent; throughput and several processes are next steps.
