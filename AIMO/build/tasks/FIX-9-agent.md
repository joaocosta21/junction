# FIX-9 — Agent: the model proposes and the gateway checks it; a run never loses an order; a recording is always named

**Scores on:** 20% (precise match, least manual correction) · 20% (controls: the model decides nothing) · 30% (the demo must not double-order or stall). From the final review round (Python reviewer findings 2, 5, 6, 10, 11, 12; silent-failure findings 1–5, 7, 10; security finding 9).
**Owns:** `src/tta/agent/`, `tests/agent/`, `fixtures/agent/`. **Hand-backs:** `AIMO/build/handback/T10.md`, `T10-followup.md`. **Read:** SPEC §3, §11.

## Findings to fix
1. **HIGH — the model's numbers are taken as given.** `parser.py`: quantity, unit, `needed_by`, `require_confirmed` and the allergen exclusions are never checked against the text; product ids are checked by substring (`"1" in "1,000"`). Add a deterministic cross-check of every proposal against the text, before the contract model is built:
   - each line's quantity must appear in the text as a number (normalise "1,000", "1 000", "1000", "1.5", "1,5"; words such as "a thousand" may be added if cheap); the unit must agree with a unit word in the text (litres/liters/l, kg/kilos, units/pieces/packs, Finnish forms where cheap);
   - `needed_by` must equal the date the parser's own calendar rule gives for the day the text names (a weekday name: the first such day after today; "today", "tomorrow"; an explicit date); a text that names no day must give no `needed_by`;
   - every allergen the text excludes ("no milk", "milk-free", "without nuts", "gluten-free", Finnish forms where cheap) must be in the proposal's exclusions, mapped through `tta.allergens`; `require_confirmed` true only when the text asks for confirmed data;
   - product ids match whole tokens of the text only.
   A disagreement is `invalid-request` naming the field and saying "the reading did not match the text" — never silently corrected. A sentence the check cannot follow (it names no number) still reports the quantity as missing, as today.
2. **HIGH — a run that fails after `place_order` loses the order.** `runner.py`: any exception after a gateway call (not only `SupplierUnavailable`) ends the run and returns it with every step done so far, the order id and status if one was placed, and a report that opens with what stopped it. `gemini.py` `_send`: every exception of the SDK or the transport becomes the module's own error with the HTTP status or the exception class name only (no SDK text in a log or an error).
3. **HIGH — a reading from a recording looks like the model's.** Implement `read(text, identity) -> Reading` on every parser class (`ModelRequestParser`, the recorded parser, `FallbackParser`): `source` MODEL / RECORDING / HAND_BUILT, `model`, `recorded_at`, and a sentence ("Read by gemini-3.6-flash.", "Gemini did not answer; read from a recording of gemini-3.6-flash made on 14 Nov 2026 at 06:14 UTC.", "Read from an answer written by hand, not by a model."). `parse_request` stays and returns `read(...).request`. `FallbackParser.model_id` names what actually answered.
4. **MEDIUM — an outage costs about 90 s per sentence, every time.** After a model call fails for unreachability, remember it for 120 s (a named constant, one per process, thread-safe): during that window the fallback answers from the recording at once, labelled, without asking Gemini; a sentence with no recording answers `supplier-unavailable` at once. Also cap one sentence's waiting: one retry instead of two for the interactive parser and runner (keep two in `record.py`).
5. **MEDIUM — the report hides the gateway's refusal or the model's silence.** `runner.py`: when the gateway refused a call, the report names that refusal (not a later "no offer yet" from the runner); when the model ends with no function call, the report says "the model stopped without …" (without an offer, without an order) and how many steps it took.
6. **MEDIUM — the agent may order any option.** `tools.py` `place_order`: only the top option of the run's latest offer (`options[0]`) may be ordered; any other id is refused as a failed step with a sentence. At most 2 `create_offer` calls per run; on `offer-stale` / `offer-expired` the runner uses `fresh_offer_id` from the problem instead of asking for a new offer.
7. **LOW — a recording is replayed for any buyer and any day.** A recording names the profile it was recorded for (`profile_id`; the hand-written and recorded files say `hotel-kitchen` for scenario 1 and the "no quantity" sentence, `allergy-ward` for scenario 2); it is served only for that profile. A recorded `needed_by` is re-resolved with the parser's own calendar rule when the recording's `today` differs from today (so "by Monday" on Sunday 15 Nov still gives 16 Nov, and on Monday 16 Nov gives 23 Nov). "Today" is the date in Europe/Helsinki.
8. **LOW — the recorder can save a failed reading.** `record.py`: write a parse recording only when the model's answer validated (an `invalid-request` for a missing fact is a valid answer and is recorded; one for an answer that did not validate twice is not); never write a run that ended because the model stopped answering.
9. **LOW — a test that cannot fail.** `tests/agent/test_guardrails.py` (the injection test near line 70): make it able to fail — a scripted model that does follow the injected instruction, and assert the gateway still orders only what the offer allows.
